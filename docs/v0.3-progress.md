# Lan Copy v0.3 实施进度

按 [v0.3 计划](v0.3-plan.md) 的四个阶段跟踪。状态以当前工作区为准；尚未验收的目标不标记为完成。

## 总览

| 阶段 | 状态 | 当前结果 |
| --- | --- | --- |
| 一：原包内梳理 | 已完成 | 在 `package main` 内按职责拆分文件，保持入口、路由和恢复顺序。 |
| 二：独立组件 | 已完成 | `textstore`、`desktop`、`updater` 已提取；原包 HTTP handler 调用组件。 |
| 三：文件存储 | 已完成 | `filestore` 统一路径、文件与目录操作、上传接收、提交/回滚和启动恢复；文件锁与资源预算由组件管理。 |
| 四：入口与 HTTP 层 | 已完成 | `app` 负责组装、启动恢复与关停；`httpserver` 负责全部路由、handler、SSE 与传输状态。根目录只保留入口、构建变量和资源嵌入。 |

## 阶段一：原包内梳理

- 根目录 `main.go` 只调用 `run`；现有命令行、实例探测、服务启动及关停流程移到 `startup.go`。
- 静态资源声明移到 `assets.go`，保留根目录的 `//go:embed web/*`。
- `routes.go` 收拢路由，`events.go` 收拢 SSE 和变更通知，`shutdown_handlers.go` 收拢网页关停协议，`network.go` 收拢地址探测和访问地址接口。
- `file_handlers.go` 收拢文件列表、下载、预览、本机文件操作和删除 HTTP 处理；`file_names.go` 收拢当前的文件名与类型函数；`http_helpers.go` 收拢响应和安全头；`server.go` 保存过渡期组装与共享状态。
- 记录现有锁与恢复顺序：`fileMu` 保护文件变更和上传提交，`textMu` 保护文本读改写，事件与传输各有状态源；启动依次迁移旧数据、恢复文本、恢复上传事务、加载上传配置。此处仅标注现状，没有移动锁或改变恢复实现。

### 验证

- `make test` 通过：26 个 Python 测试、5 个 Node 脚本和 `go test ./...`。
- `go vet ./...`、`go build .`、`go run . -h` 通过。
- `CGO_ENABLED=0` 的 Windows amd64、Linux amd64、macOS arm64 交叉构建通过。交叉构建不代表对应平台的运行行为已验证。
- 本阶段是纯职责拆分；未运行 Docker 构建和发布打包，留到新增 `internal/` 构建输入时一并检查。

## 阶段二：独立组件

- `internal/textstore` 拥有文本数据目录、读改写锁、容量约束、备份替换及启动恢复。HTTP handler 保留 JSON 解析、状态码与变更通知，按组件错误映射现有文案。持久化故障注入测试已随实现迁移。
- `internal/desktop` 拥有自启动状态及锁，收拢控制台、打开文件、系统语言和平台自启动实现。HTTP 层继续负责本机访问与来源策略。macOS、Windows 平台测试及自启动配置测试已随实现迁移。
- `internal/updater` 拥有更新互斥状态、包解压与验签、Release 查询、辅助进程、健康检查和回滚。根目录保留 `version`、`updatePublicKey` 链接变量；HTTP handler 保留请求访问策略及响应。版本比较、Release 地址和故障测试已随实现迁移，完整更新流程仍由根包集成测试覆盖。
- `Makefile` 将 `internal/` 纳入构建输入；`Dockerfile` 复制 `internal/`。根目录入口和 `buildinfo.Path == "lan-copy"` 更新身份保持不变。

### 验证

- 文本存储迁移后、桌面迁移后及更新迁移后分别运行 `go test ./...`，均通过。
- 阶段二最终的完整测试、vet、竞态检查和跨平台构建结果记录在下方“本轮验证”。

## 阶段三：文件存储

- `internal/filestore` 拥有共享路径及跨平台名称校验、文件和目录操作、冲突处理与文件变更锁。根包只负责请求解析、访问控制、状态码、响应和文件变更通知。
- 上传清单校验、预检会话、资源配置及预算、事务接收、暂存写入、提交和回滚已迁入组件。HTTP 层保留 multipart 协议与现有错误文案；事务记录、暂存目录及配置文件的位置和格式保持不变。
- 启动恢复直接调用 `filestore.RecoverTransactions`，不再构造 HTTP `server`。现有目录、冲突、替换失败、回滚和重启恢复集成测试保持通过；预算写入与资源配置测试随实现迁入组件。

### 验证

- `make test` 通过：26 个 Python 测试、5 个 Node 脚本和 `go test ./...`；`go vet ./...` 与 `git diff --check` 通过。
- `go run . -h` 与 Windows amd64、Linux amd64、macOS arm64 的 `CGO_ENABLED=0` 交叉构建通过。跨平台编译不代表对应平台运行已验证。
- 竞态检查与 Docker 构建状态见下方“阶段三本轮验证”。

## 阶段四：入口与 HTTP 层

- `internal/app` 负责参数解析、默认目录及应用数据迁移、启动恢复顺序、组件组装、实例探测、监听、信号和关停。根目录仅有 `main.go`、`startup.go`、`assets.go`，保留 `-X main.version`、`-X main.updatePublicKey` 和 `//go:embed web/*`。
- `internal/httpserver` 拥有路由、所有业务 handler、访问策略、静态资源、SSE 订阅、传输登记与关停确认。它只依赖具体组件，不依赖 `app`；组件不依赖 HTTP 层。文件和文本一致性锁仍分别归所属组件。
- HTTP 测试迁入 `internal/httpserver`，启动迁移与恢复测试迁入 `internal/app`。更新进程测试从模块根目录构建真实主程序；CI 的发布包验签目标同步改为 `./internal/httpserver`。开发文档已更新代码位置。

### 验证

- `make test`（26 个 Python 测试、5 个 Node 脚本和 Go 测试）、`go vet ./...`、`go test -race ./...`、`git diff --check` 与 `go run . -h` 均通过。
- Windows amd64、Linux amd64、macOS arm64 的 `CGO_ENABLED=0` 主程序构建及 HTTP 测试二进制交叉编译通过。交叉编译不代替对应平台运行。
- 使用临时 Ed25519 密钥在独立临时目录完成 `make build`，生成签名的 Windows 与 macOS 包及校验和；`TestPublishedReleasePackages` 对这两个包验签通过。构建版本和公钥仍通过根目录 `main` 链接变量传入，`go version -m` 显示主程序路径为 `lan-copy`。
- 本机 Docker 守护进程不可连接（OrbStack socket 不存在），未运行 Docker 构建；Dockerfile 已复制 `internal/`，仍需在 Docker 可用环境验证。
