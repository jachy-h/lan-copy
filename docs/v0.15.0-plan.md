# Lan Copy v0.15.0 Homebrew Formula 分发计划

更新日期：2026-11-24。状态：**已批准并完成实现，自动化验证通过，待人工验收**。

## 背景与目标

Lan Copy 目前在 GitHub Releases 提供两个产物：

- `Lan-Copy-macOS-Apple-Silicon.tar.gz`（内含 `Lan-Copy-macOS-arm64/lan-copy`、`update.json`、`update.sig`、`README.md`）
- `Lan-Copy-Windows-amd64.zip`

macOS 用户需要手动下载、解压、移动二进制、处理 Gatekeeper 与登录启动项。本版把 macOS 安装收敛为一行命令：

```bash
brew install jachy-h/jachy-h/lan-copy
brew upgrade lan-copy
```

目标是让 Homebrew 成为 macOS 上的**首选手工安装方式**，同时不改变现有 Release 产物、应用内自动更新、插件与 HTTP API 语义。

## 已确认的决策

- **二进制 Formula，不从源码构建**：Homebrew 安装的就是 Release 里的同一个 `lan-copy` 二进制，与 `TestPublishedReleasePackages` 校验过的产物一致，安装不需要 Go/Node 工具链，也不会因为源码构建产生第二个二进制形状。
- **只支持 macOS Apple Silicon**：现有 Release 只有 `darwin/arm64` 产物。Formula 用 `depends_on :macos` + `depends_on arch: :arm64` 明确拒绝 Intel Mac 与 Linux，并给出可读错误，不做含糊的 `on_macos` 通配，也不假装支持未发布的架构。
- **Tap 为唯一事实来源**：`Formula/lan-copy.rb` 的 `desc`、`install`、`service`、`caveats`、`test` 由 Tap 仓库维护；发布流程只改 `url` 与 `sha256` 两行。
- **Tap 更新挂在既有 tag 发布流程上**：在 `.github/workflows/release.yml` 的 `release` job 之后新增 `homebrew` job，仅在 `refs/tags/v*` 时运行，与 Umbragate 的 `update-homebrew-tap` 模式一致。
- **SHA256 只来自发布流程产物**：从 Release 的 `SHA256SUMS` 读取 macOS 归档校验值，绝不猜测、绝不复用上一次的值。
- **推送前先验证**：`homebrew` job 在 macOS runner 上对**更新后的**formula 执行 `ruby -c`、`brew style`、`brew audit --strict --online`，全部通过才 commit 与 push，不做“先推再等 Tap CI 报警”。
- **CI 不写死版本号**：`url`/`sha256` 由 `scripts/update_homebrew_formula.py` 从 Release 元数据推导，脚本对“找不到 URL 行”“找不到 sha256 行”“版本不一致”“归档缺失”一律报错退出。
- **应用内更新与 Homebrew 共存**：`install` 只装二进制，不装 `update.json`/`update.sig`，并在 `caveats` 中要求用 `brew upgrade lan-copy` 升级；应用自身的在线更新按钮仍然可用，但会写入 Cellar，属于已知限制。
- **Tap 侧 Token 最小权限**：使用 fine-grained PAT（仅 `jachy-h/homebrew-jachy-h` 的 `contents: read/write`）存为 `jachy-h/lan-copy` 的 `HOMEBREW_TAP_TOKEN`；`release.yml` 其余 job 保持 `contents: read`，新 job 自己的 `permissions` 也只声明 `contents: read`（写 Tap 靠 Token，不靠 `GITHUB_TOKEN`）。Secret 缺失时跳过并给出警告，不让已有发布流水线硬失败。

## 已确认决策（补充）

1. **许可证**：确认使用 MIT。新增 `LICENSE`（Copyright (c) 2026 Jachy），formula 写 `license "MIT"`，README 增加许可证章节。
2. **初始 Formula 版本**：确认锚定 `v0.8.1`（`sha256 fe6cb38a…1c9f37`），下一次 tag 发布后由 CI 自动对齐。

## 原待确认决策（已结）

1. **许可证**：`jachy-h/lan-copy` 目前没有 `LICENSE` 文件，GitHub 也没有识别到许可证。Homebrew `brew audit` 要求 formula 有 `license`。
   - 方案 A（推荐）：给项目加 MIT `LICENSE` 并在 README 注明，formula 写 `license "MIT"`。
   - 方案 B：暂不授权许可，formula 写 `license :cannot_represent`。可审计通过，但对使用者不友好。
2. **初始 Formula 版本**：当前最新已发布 Release 是 `v0.8.1`（`VERSION` 已到 `0.14.0-build4`，但未发布 tag）。计划用真实校验值把 `Formula/lan-copy.rb` 初始化为 `v0.8.1`：
   - `url`：`https://github.com/jachy-h/lan-copy/releases/download/v0.8.1/Lan-Copy-macOS-Apple-Silicon.tar.gz`
   - `sha256`：`fe6cb38a213708405f9051c78f17bbca426053397003862953757eee001c9f37`（本地下载实测）
   这样 Tap 上线即可用；下一次 `make publish` 打出 `v0.15.0-build1` 时由 CI 自动对齐到新版本。如果希望 Tap 直接指向一个全新 tag，需要先发布 `v0.15.0-build1`。

## 非目标

- 不新增 Windows / Linux / Intel Mac 产物，不改 `Makefile` 的构建矩阵。
- 不改 Release 归档布局、`update.json` 字段、签名流程、`SHA256SUMS` 格式。
- 不改变应用内更新、插件协议、HTTP API、上传 Hook 或前端资源。
- 不做 Cask、不做公证（notarization）、不改 Gatekeeper/隔离属性语义。
- 不在 CI 中执行真实 `brew install lan-copy`（安装验证留给人手动做）。
- 不在 `release.yml` 里复制一份 formula 模板；模板只在 Tap 仓库存在。

## Formula 设计

`~/work/homebrew-jachy-h/Formula/lan-copy.rb`（Tap 仓库，类名 `LanCopy`）：

```ruby
class LanCopy < Formula
  desc "Minimal zero-dependency LAN file and text sharing tool"
  homepage "https://github.com/jachy-h/lan-copy"
  url "https://github.com/jachy-h/lan-copy/releases/download/v0.8.1/Lan-Copy-macOS-Apple-Silicon.tar.gz"
  sha256 "fe6cb38a213708405f9051c78f17bbca426053397003862953757eee001c9f37"
  license "MIT"

  depends_on :macos
  depends_on arch: :arm64

  def install
    bin.install "Lan-Copy-macOS-arm64/lan-copy"
  end

  service do
    run [opt_bin/"lan-copy", "-dir", var/"lan-copy"]
    keep_alive true
    working_dir var
    log_path var/"log/lan-copy.log"
    error_log_path var/"log/lan-copy.log"
  end

  def caveats
    <<~EOS
      Start in the background:
        brew services start lan-copy

      Open http://localhost:8080 after startup.

      Upgrade with Homebrew, not the in-app updater:
        brew upgrade lan-copy

      Run in the foreground with your own directory:
        lan-copy -dir ~/共享文件夹-lancopy
    EOS
  end

  test do
    port = free_port
    (testpath/"share").mkpath
    pid = fork do
      exec bin/"lan-copy", "-listen", "127.0.0.1:#{port}", "-dir", testpath/"share"
    end

    begin
      20.times do
        sleep 0.5
        break if system("curl", "-fsS", "http://127.0.0.1:#{port}/healthz", out: File::NULL, err: File::NULL)
      end
      assert_equal "ok", shell_output("curl -fsS http://127.0.0.1:#{port}/healthz").strip
      app = JSON.parse(shell_output("curl -fsS http://127.0.0.1:#{port}/api/app"))
      assert_match(/\A\d+\.\d+\.\d+/, app["version"])
      assert_equal "darwin", app["os"]
    ensure
      Process.kill("TERM", pid)
      Process.wait(pid)
    end
  end
end
```

要点：

- `test` 真正启动安装出来的二进制，用 `/healthz` 与 `/api/app` 断言，而不是只打印 `--help`。
- `service` 把数据目录放在 `var/lan-copy`，避免 `brew services` 以 `/` 为工作目录时把 `共享文件夹-lancopy` 写进意外位置。
- `caveats` 明确 `brew services`、访问地址、升级方式与前台用法。
- 不写 `version`（URL 自带版本号，`brew audit --strict` 不允许冗余 `version`）。

## CI 变更（`jachy-h/lan-copy`）

在 `.github/workflows/release.yml` 末尾新增 job：

```yaml
  homebrew:
    name: Update Homebrew tap
    if: startsWith(github.ref, 'refs/tags/v')
    needs: [metadata, release]
    runs-on: macos-latest
    timeout-minutes: 20
    permissions:
      contents: read
    steps:
      - name: Check whether the tap token is configured
        id: tap
        env:
          HOMEBREW_TAP_TOKEN: ${{ secrets.HOMEBREW_TAP_TOKEN }}
        run: |
          if [ -z "$HOMEBREW_TAP_TOKEN" ]; then
            echo '::warning::Set the HOMEBREW_TAP_TOKEN repository secret to update the tap automatically.'
            echo "configured=false" >> "$GITHUB_OUTPUT"
            exit 0
          fi
          echo "configured=true" >> "$GITHUB_OUTPUT"
      # 1. checkout 源码（拿脚本）
      # 2. 用 HOMEBREW_TAP_TOKEN checkout jachy-h/homebrew-jachy-h 到 tap/
      # 3. gh release download "${{ github.ref_name }}" --pattern SHA256SUMS --dir dist
      # 4. python3 scripts/update_homebrew_formula.py --formula tap/Formula/lan-copy.rb \
      #      --checksums dist/SHA256SUMS --version "$RELEASE_VERSION" \
      #      --asset Lan-Copy-macOS-Apple-Silicon.tar.gz
      # 5. 把 tap/ 注册为本地 tap（symlink + brew trust），对更新后的 formula 跑
      #    brew style 与 brew audit --strict --online
      # 6. git diff 为空则退出；否则 github-actions[bot] 提交并 push
```

顺序细节：

- `needs: [metadata, release]`：必须等 `SHA256SUMS` 已经上传到 Release，再从 Release 下载校验文件，CI 与用户拿到的归档完全一致。
- 只在 tag 上运行；`workflow_dispatch` 与分支推送不动 Tap。
- Secret 缺失时 exit 0（避免流水线红），但在 Step Summary 写警告。
- 提交信息：`chore: update lan-copy v<version>`；提交文件仅 `Formula/lan-copy.rb`（Tap 的 `git diff --quiet` 保证无空提交）。
- Tap 仓库自己的 `validate.yml` 在 push 到 `main` 后仍会再跑一遍完整校验，作为第二道闸门。

## 脚本与测试（`jachy-h/lan-copy`）

新增 `scripts/update_homebrew_formula.py`：

- 参数：`--formula`、`--checksums`、`--version`、`--asset`、可选 `--dry-run`。
- 读取 `SHA256SUMS`，按“`<sha256>  <name>`”解析；`--asset` 必须恰好命中一行，命中 0 行或多行报错。
- 在 formula 中定位**唯一**的 URL 行：以 `https://github.com/jachy-h/lan-copy/releases/download/v` 开头且以 `/<asset>` 结尾；下一行必须是 `sha256 "…"`。定位失败或有多处匹配时报错。
- 校验 URL 里的版本号等于 `--version`，避免把 v0.14 的校验值写到 v0.15 的 URL 下。
- 原子写入：写临时文件后 `os.replace`，失败时原文件不变。
- 输出一行摘要供 CI 打印（版本、sha256、文件名）。

新增 `scripts/test_update_homebrew_formula.py`（`unittest`，跟随现有 `make test` 的 `scripts` 测试发现规则）：

- 正常更新：URL 与 sha256 同时变化，其余行逐字节不变。
- 版本不一致、归档缺失、sha256 行缺失、URL 行重复：均返回非零并保持原文件不变。
- 已是最新版本：无写入。
- `--dry-run`：只打印不写盘。

## 风险与后续

- **初始版本落后**：Tap 初始化为 `v0.8.1`，用户会看到旧版本，直到下一次 tag 发布。这是“不虚构版本”的代价，可通过先发 tag 再合并 Tap 改动规避。
- **应用内更新与 brew 冲突**：应用内更新会写 Cellar，`brew upgrade` 之后版本信息可能不一致。已在 `caveats` 提示，后续可考虑加 `--no-self-update` 之类的运行时开关（不在本版范围）。
- **audit 对 macOS-only tool 的判定**：`depends_on :macos` + `depends_on arch: :arm64` 是否被 `--strict` 判为多余，需要在实施时用本机 `brew audit` 实测并按提示调整（例如改为平台块内 URL）。
- **Token 权限**：PAT 过期会让 Tap 停在旧版本，`homebrew` job 会以 push 失败显式报错（不是静默跳过）。
- **后续扩展**：若将来发布 `darwin/amd64` 或 `linux` 产物，再在 formula 中增加对应 URL/sha256；本版不做前瞻设计。
