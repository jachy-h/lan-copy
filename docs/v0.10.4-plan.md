# Lan Copy v0.10.4 构建号版本规则计划

更新日期：2026-11-20。状态：**已批准并完成实现，自动化验证通过，待人工验收**。

## 背景与目标

当前版本号只允许 `MAJOR.MINOR.PATCH`：`make build` 读取并复用 `VERSION`，`make publish` 自动递增 patch，构建失败不改版本，但同一版本无法区分“第几次构建”。本次把发布版本改为带构建号的 `x.y.z-build{c}`，例如 `0.8.1-build3` 表示 `0.8.1` 的第 3 次构建。

目标：

1. `VERSION`、程序内版本、`update.json`、Git 标签和 GitHub Release 统一使用 `x.y.z-build{c}`。
2. `make build` 和 `make publish` 每执行一次构建，构建号 `+1`。
3. 基础版本 `x.y.z` 升级时，构建号归零，首次构建为 `-build1`。
4. 构建失败、预览（`make -n`）和 CI 重跑不推进构建号；CI 使用已提交的完整版本。
5. 在线更新按 `x.y.z` 后 `build{c}` 的顺序比较，兼容历史无构建号的 `x.y.z` 发布。

## 已确认的边界

- 构建号只描述同一基础版本的构建次数，不改变基础语义：`0.8.1-build3` 与 `0.8.1-build4` 仍是同一个 `0.8.1` 版本。
- `x.y.z`（无后缀）继续合法，视为 `build0` 或“待构建的新基础版本”；历史标签 `v0.8.1` 仍能被识别和比较。
- 新基础版本的第一次构建是 `-build1`；不产生 `-build0` 的发布制品。
- 基础版本升级由开发者显式指定（编辑 `VERSION` 为 `x.y.z`，或 `make build VERSION=x.y.z`），`make publish` 不再自动递增 patch。
- 构建号单调递增，不能通过普通构建把版本降到当前 `VERSION` 以下；发布要求严格大于当前版本。
- 不改更新包的签名、平台校验、安装、回滚和 Recovery 语义；只扩展版本字符串与比较规则。

## 非目标

- 不引入 SemVer 预发布标识（`-beta.1`、`+meta`）、提交哈希或日期版本。
- 不把构建号写入文件名、附件名、共享目录或插件协议。
- 不实现按构建号自动清理旧发布、自动归档或发布回滚。
- 不改变 `dev` 开发版本行为：直接 `go build` 且未传 `-X main.version` 时仍为 `dev`。

## 一、版本模型

### 1.1 语法

```text
version := "x.y.z" | "x.y.z-build{c}"
x,y,z   := 0 | [1-9][0-9]*
c       := [1-9][0-9]*
```

- 统一使用小写 `build` 和十进制、无前导零的构建号。
- 标签为 `v` + 完整版本，例如 `v0.8.1-build3`。
- 内部展示和 `update.json` 保存不带 `v` 的完整版本。

### 1.2 比较

比较顺序：

1. 依次比较 `x`、`y`、`z` 数值。
2. 基础版本相同时比较构建号，无后缀按 `0` 处理。
3. 因此 `0.8.1` < `0.8.1-build1` < `0.8.1-build2` < `0.8.2-build1`。

### 1.3 递增与归零

| 当前 `VERSION` | 操作 | 结果 |
| --- | --- | --- |
| `0.8.1` | `make build` | `0.8.1-build1` |
| `0.8.1-build3` | `make build` | `0.8.1-build4` |
| `0.8.1-build3` | 编辑为 `0.8.2` 后 `make build` | `0.8.2-build1` |
| `0.8.1-build3` | `make build VERSION=0.8.2` | `0.8.2-build1` |
| `0.8.1-build3` | `make build VERSION=0.8.1-build3` | `0.8.1-build3`（CI/重跑原样使用） |
| `0.8.1-build3` | `make publish` | `0.8.1-build4`，标签 `v0.8.1-build4` |
| `0.8.1-build3` | `make publish VERSION=0.9.0` | `0.9.0-build1`，标签 `v0.9.0-build1` |

- 显式完整版本（带 `-buildN`）原样使用，不自动加一，供 CI、重跑和本地部署脚本使用。
- 显式基础版本（不带后缀）表示“开始构建该基础版本”：高于当前基础版本时从 `-build1` 开始，等于当前基础版本时视为下一次构建，低于当前基础版本时报错。
- 显式完整版本可等于当前版本用于重建；低于当前版本时报错。
- 所有保存都只在构建成功且产物齐全后发生。

## 二、构建脚本

### 2.1 `scripts/build_release.py`

- 新增统一的版本解析与格式化函数，接受 `x.y.z` 和 `x.y.z-build{c}`，拒绝非法、前导零和 `build0`。
- `build_version(version_file, override)` 改为返回本次实际构建版本：
  - 无 override：读取 `VERSION`，无后缀或 `build0` 从 `-build1` 开始，否则构建号 `+1`。
  - override 为完整版本：原样使用。
  - override 为基础版本：按 1.3 的归零/递增规则计算。
  - 结果低于当前已保存版本时抛出明确错误。
- 移除按 patch 递增的 `next_version`；新增供 publish 复用的下一构建版本函数。
- 保留锁、预览检测、失败不落盘、产物缺失报错、摘要输出和原子写入。
- 构建摘要中的 `Version:` 显示完整版本。

### 2.2 `scripts/publish_release.py`

- 默认发布版本改为当前基础版本的下一次构建，例如 `0.8.1-build3` → `0.8.1-build4`；不再自动递增 patch。
- 支持 `VERSION=0.9.0`（新基础版本，首次为 `0.9.0-build1`）和 `VERSION=0.9.0-build2`。
- 校验发布版本严格大于当前 `VERSION`，并保留本地/远端标签存在检查。
- 确认提示、预览输出、版本提交信息、附注标签和 `git push --atomic` 都使用完整版本。
- 标签格式为 `v{x.y.z-buildN}`；版本提交仍只提交 `VERSION`。

### 2.3 `scripts/ci_release_version.py`

- 接受带构建号的 `VERSION`。
- 标签必须严格等于 `v` + 已提交完整版本，例如 `VERSION=0.8.1-build3` 只接受 `v0.8.1-build3`。
- 分支构建和标签构建都原样返回已提交版本，不递增、不修改文件。

### 2.4 Makefile 与本地发布入口

- `Makefile` 的默认回退版本仍为 `0.1.0`；`make build` 把空 `VERSION` 交给 Python 递增。
- `make windows`、`make macos`、`make artifacts` 继续原样使用已保存的完整版本，不递增。
- `LDFLAGS`、`update-manifest` 和 Windows PowerShell 打包流程接收完整版本字符串，无需结构化解析。
- `scripts/release-local.mjs` 与 `scripts/deploy-target.mjs` 的 `--version` 校验扩展到 `x.y.z-build{c}`；帮助文案改用新格式。
- `make deploy`、`make publish`、`make build` 之间传递完整版本，避免二次递增。

## 三、在线更新兼容

### 3.1 `internal/updater/release.go`

- 正式版本正则扩展为 `^v?x.y.z(-build[1-9][0-9]*)?$`，历史无后缀标签继续有效。
- `CompareVersions` 先比较基础版本，再比较构建号；无后缀视为构建号 0。
- `Latest` 继续拒绝 draft 和 prerelease；带构建号的正式 Release 视为有效正式发布。

### 3.2 兼容性

- 已安装的无后缀版本（如 `0.8.1`）可以升级到 `0.8.1-build1` 及更高版本。
- 已安装的 `0.8.1-build3` 不会把旧的 `0.8.1` 识别为新版本。
- 更新包内 `update.json` 的 `version` 与 Release 标签继续要求完全一致。
- 更新历史仍按完整版本字符串保留最近两个版本，不需要迁移。

## 六、实施顺序

2. 更新 `publish_release.py` 和 `ci_release_version.py`。
3. 更新 Makefile 相关说明、本地发布 Node 脚本及参数校验。
4. 扩展 Go 更新器版本正则与比较逻辑。
5. 更新 Python、Node、Go 测试。
6. 更新文档、计划与进度记录。
7. 运行全量测试、构建检查和预览命令，记录验证结果。

## 七、风险与限制

- 旧脚本或外部 CI 若假设 `VERSION` 只有三段，会在读取后失败；本次同步更新仓库内所有入口和文档。
- 同一基础版本可能产生很多构建号，GitHub Release 和标签数量随之增加；不自动清理历史标签。
- `make build` 现在会修改 `VERSION`，本地连续构建会产生未提交改动；发布前仍需按现有流程提交代码和 `VERSION`。
- CI 分支构建使用已提交版本，不推进构建号；开发者需在本地完成构建号递增并提交。
- 不带构建号的历史标签仍合法，因此比较时无后缀等同 `build0`；不会把 `0.8.1` 与 `0.8.1-build0` 区分。
