# Lan Copy v0.16.2 计划：CI 去掉 macOS runner，macOS 验证与 Homebrew 更新回到本机

更新日期：2026-11-24。状态：**已批准**。

## 背景

发布 `v0.16.0-build1` 时 GitHub Release 正常发布，但 `Update Homebrew tap` job 在 `macos-latest` 上 **从未获得 runner**：日志为 `The job was not acquired by Runner of type hosted even after multiple attempts`，伴随 `Due to capacity constraints, jobs targeting macOS arm64 runners may experience longer queue times`，排队 15 分钟后被平台取消。同一次运行的其它 job 全部正常：ubuntu 测试 1.5 分钟、windows 测试 1.7 分钟、浏览器集成 3 分 12 秒、构建 2 分钟、发布 13 秒。

结论：排队只发生在 macOS arm64 hosted runner 上。该 job 唯一依赖 macOS 的原因是执行 `brew style`、`brew audit --strict --online`、`brew trust`，而这三项与 Tap 仓库自己的 `validate.yml` 重复，且无法在容量不足时完成。

## 目标

1. `.github/workflows/release.yml` 中不再出现任何 macOS runner；发布流程不再因为 macOS 容量排队而中断。
2. macOS 专属验证（darwin `go test`、`brew style`、`brew audit --strict --online`）和 Tap 公式更新改由本机 Makefile 目标完成。
3. `make publish` 在推送标签后自动等待 Release 资产上线，再更新并推送 Tap 公式；失败时给出可重试的明确提示。
4. 不改变产品行为：无 Go 代码、前端资源、HTTP API、插件协议、发布包布局与更新包格式改动。

## 已确认的决策

- **CI 保留跨系统验证**：`test`（ubuntu + windows）、`browser`（ubuntu-24.04）、`build`（ubuntu）、`release`（ubuntu）全部不变。它们启动时间稳定在数分钟内，并保留“干净机器独立构建/验证”的价值。
- **删除 `homebrew` job**：其职责整体搬到本机。仓库 Actions secret `HOMEBREW_TAP_TOKEN` 随之作废，可在仓库设置中手动删除（本计划不改仓库设置）。
- **浏览器测试留在 ubuntu CI**：Playwright 依赖 node、浏览器二进制与 `go build`，与宿主系统无关。仅额外提供一个可选的本地 `make browser-test` 目标，用于 WebKit 相关疑点排查（Playwright 的 webkit 在 Linux 是 WebKitGTK、在 macOS 是原生构建，文件选择器/下载/拖拽行为存在差异，本项目的上传下载正好落在该区域），**不并入 `make publish` 链路**，避免发布变慢。
- **本地 Tap 直接操作 `brew tap` 的 git clone**：`$(brew --repository)/Library/Taps/jachy-h/homebrew-jachy-h` 是可直接提交推送的仓库，不需要 CI 里的 symlink 与 `brew trust` 临时处理。
- **校验和以已发布 Release 为权威**：默认从 `gh release download v<version> -p SHA256SUMS` 读取，同时天然证明附件已上线；`--checksums` 可改用本地 `release/SHA256SUMS` 离线执行。
- **校验失败不落盘**：`ruby -c`、`brew style`、`brew audit --strict --online` 任一失败，公式文件恢复原内容，工作区保持干净，不产生提交。
- **凭据走本机 git 配置**：推送 Tap 使用本地 `origin` 的既有凭据（当前为 GitHub CLI 授权），不再需要 `HOMEBREW_TAP_TOKEN`。
- **绝不吞掉失败**：Release 未就绪时按 `HOMEBREW_WAIT` 轮询（`make publish` 默认 900 秒），超时给出“确认 Actions 发布完成后再执行 `make homebrew`”的提示并以非零码退出。

## 代码改动

### `.github/workflows/release.yml`

- 删除整个 `homebrew` job（`runs-on: macos-latest`），文件在 `release` job 之后结束。
- 其它 job、权限、并发、触发条件不变。

### `Makefile`

新增变量：

```make
HOMEBREW_TAP       ?= jachy-h/jachy-h
HOMEBREW_FORMULA   ?= lancopy
HOMEBREW_ASSET     ?= Lan-Copy-macOS-Apple-Silicon.tar.gz
HOMEBREW_REPO      ?= jachy-h/lan-copy
HOMEBREW_TAP_DIR   ?= $(shell brew --repository 2>/dev/null)/Library/Taps/jachy-h/homebrew-jachy-h
HOMEBREW_WAIT      ?= 0
PUBLISH_HOMEBREW_WAIT ?= 900
```

新增目标：

| 目标 | 行为 |
| --- | --- |
| `require-macos` | 断言 `uname -s` 为 Darwin，非 macOS 直接停止；被 `release-test`、`homebrew-check`、`homebrew` 复用 |
| `homebrew-check` | 只读校验本地 Tap 公式：`ruby -c`、`brew style`、`brew audit --strict --online --formula` |
| `homebrew` | 调用 `scripts/publish_homebrew.py`：同步 Tap → 取校验和 → 改写公式 → 校验 → 提交推送 |
| `browser-test` | 可选：`npm ci` + `playwright install` + `npm run test:browser`，不进入发布链路 |

修改：

- `release-test` 改为依赖 `require-macos`，删除内联的平台断言，其余命令不变。
- `publish` 在发布脚本成功后读取新的 `VERSION` 与执行前快照比较：只有确实产生了版本提交才继续执行 `$(MAKE) homebrew VERSION=<新版本> HOMEBREW_WAIT=$(PUBLISH_HOMEBREW_WAIT)`；取消或预览模式直接跳过并说明原因。

### 新增 `scripts/publish_homebrew.py`

按仓库既有惯例（发布相关逻辑集中在 `scripts/`，与 `test_*.py` 相邻），编排逻辑放 Python，Makefile 只做入口。步骤：

1. 校验版本号格式（复用 `build_release.release_version`）；
2. 定位 Tap 目录与 `Formula/<formula>.rb`，缺失时提示 `brew tap jachy-h/jachy-h`；
3. 非 `--dry-run` 时检查 Tap 工作区干净、当前分支正确，`git fetch` 后 `git merge --ff-only origin/<branch>` 同步；
4. 取得 `SHA256SUMS`：`--checksums` 指定文件，否则 `gh release view` 轮询附件出现（最多 `--wait` 秒）后 `gh release download`；
5. 复用 `update_homebrew_formula.updated_formula()` 计算新文本（只改 `url` 与 `sha256`）；内容一致则打印“已是最新”并退出 0；
6. 写入公式后跑 `ruby -c`、`brew style`、`brew audit --strict --online --formula`；任一失败则恢复原文件并报错；
7. `git add` + `git commit -m "chore: update lancopy v<version>"` + `git push origin HEAD:<branch>`（`--no-push` 可跳过推送）；
8. `--dry-run` 只打印将发生的改动，不写文件、不提交、不推送。

可注入的 `run` / `sleep` / `echo` 便于单测，不依赖真实网络与 brew。

### 新增 `scripts/test_publish_homebrew.py`

覆盖：

- 公式已指向目标版本时不提交、不推送；
- Tap 工作区脏、分支不对、公式文件缺失时报错；
- `--wait` 在附件出现前重复轮询，出现后使用其校验和；超时报错文案；
- 校验失败时公式文件恢复为原内容；
- `--dry-run` 不写文件、不提交；
- 提交信息与推送目标正确。

### 版本

## 验证

```bash
python3 -m unittest discover -s scripts -p 'test_*.py'
go vet ./...
go test ./...
make homebrew-check          # 本机 macOS：ruby -c + brew style + brew audit
make -n publish              # 预览发布链路，确认末尾接入 homebrew
```

人工验收：

1. 本机 `make homebrew HOMEBREW_WAIT=0`（Release 已发布时）能把 Tap 公式更新到当前版本并推送成功；
2. 故意把公式 `sha256` 改坏后执行 `make homebrew-check`，`brew audit` 失败且不产生提交；
3. 推送新标签后确认 Actions 列表里**没有** macOS job，`make publish` 在等待后自动完成 Tap 更新；
4. 无 Homebrew 环境的机器上执行 `make homebrew`，`require-macos` 或脚本给出明确失败提示。

## 不做的部分

- 不把 ubuntu/windows 测试、浏览器集成、打包与 Release 发布搬到本机（不减少排队，只降低独立验证价值）。
- 不改 Tap 仓库的 `validate.yml`（它仍跑在 `macos-latest`，推送后才排队，不阻塞发布；如需改为 ubuntu 属另一仓库改动）。
- 不新增多平台产物（linux-amd64、windows-arm64、macOS Intel）。
- 不引入自托管 runner。
- 不删除仓库 secret（`HOMEBREW_TAP_TOKEN` 作废由维护者手动在设置中删除）。

## 风险与后续

- **本机成为 Tap 更新唯一入口**：发布者必须装有 Homebrew、已 `brew tap jachy-h/jachy-h`、`gh` 已登录。文档中明确记录；缺失时目标立即失败并提示修复方式。
- **本地 Tap clone 可能过期**：脚本执行 `git fetch` + `git merge --ff-only`，落后则自动快进，分叉则报错要求手动处理。
- **等待窗口**：`make publish` 会在标签推送后等待最多 15 分钟让 Release 就绪；超时不修改 Tap，可稍后单独执行 `make homebrew HOMEBREW_WAIT=900`。
- **WebKit 覆盖略降**：本地不再是常规门禁，ubuntu CI 的 WebKitGTK 与 macOS WebKit 存在行为差异，已通过可选 `make browser-test` 保留排查手段。
- **后续可选**：Tap 仓库 `validate.yml` 改 `ubuntu-latest` 以彻底清除该仓库的 macOS 排队；把 `publish_homebrew.py` 扩展为同时更新 README 版本行。
