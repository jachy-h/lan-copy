# Lan Copy v0.3 架构优化计划

## 背景与目标

当前 Go 代码主要平铺在根目录，使用同一个 `main` 包。这符合 Go 对单命令项目的组织方式；随着文件共享、文本存储、上传恢复、自动更新和桌面集成功能增加，包内职责与状态的耦合已成为维护成本的主要来源。

本计划承接 `v0.2-plan.md` 中“按职责划分内部模块”的方向，专注于包边界和依赖整理。保持单进程、单二进制、嵌入式前端和本地文件系统存储，保留 `go run .`、`go build .` 入口。功能增强和存储格式升级另行规划。

本文描述的是目标与实施步骤，不代表重构已经完成。长期架构规则见根目录 `AGENTS.md`。

## 现状评估

- `main.go` 同时包含程序启动、服务组装、HTTP 路由、文件处理、SSE、网络探测和退出逻辑。
- `server` 持有文件与文本锁、更新服务、自启动服务、订阅者及应用生命周期状态，具体能力直接依赖同一接收者。
- `text.go` 混合 HTTP 处理与文本持久化；`update.go` 混合 HTTP 接口、签名验证、解包、更新助手与进程管理。
- `upload_tree.go` 的恢复逻辑通过构造 `server` 复用路径解析，说明文件能力尚未形成独立边界。
- 平台实现已通过文件名后缀和构建约束分离，测试与实现相邻，这些做法应延续。

Go 官方允许根目录中的多个文件共同组成 `main` 包，也建议将逐渐独立的实现放入 `internal/`。`cmd/` 是常见约定，并非本项目当前必须采用的结构。参考：[Organizing a Go module](https://go.dev/doc/modules/layout)。

## 目标目录与职责

以下结构逐步形成，不预先创建空包：

```text
lan-copy/
├── go.mod
├── main.go                  # 薄入口：构建变量、依赖传入、退出码
├── assets.go                # go:embed web/*，提供前端资源
├── internal/
│   ├── app/                 # 参数解析、依赖组装、启动与关停协调
│   ├── httpserver/          # 路由、handler、中间件、SSE、HTTP 错误映射
│   ├── filestore/           # 路径策略、文件操作、上传提交、回滚与恢复
│   ├── textstore/           # 文本读写、容量约束、持久化与恢复
│   ├── updater/             # Release 查询、验签、解包、更新助手与回滚
│   └── desktop/             # 自启动、控制台、打开文件、系统语言
├── web/
├── scripts/
│   └── update-manifest/     # 现有发布辅助命令
├── docs/
├── Makefile
└── Dockerfile
```

各包的测试随实现迁移。平台文件放进所属功能包：例如自启动平台实现归 `desktop`，更新进程平台实现归 `updater`，目录同步平台实现随文件持久化能力归属。

应用数据目录的定位与旧数据迁移由 `app` 协调；各存储组件负责自身数据格式与恢复规则。仅在确有重复实现和稳定边界时，提取小型持久化辅助包。

## 依赖与状态边界

依赖保持单向：

```text
main → app → httpserver → filestore / textstore / updater / desktop
         └────────────→ 具体组件
```

- `main` 保留版本、公钥等构建变量，将配置和静态资源传给 `app`；业务包不导入 `main`。
- `app` 负责组装、启动恢复顺序、信号处理和退出协调，避免成为新的业务实现集中点。内部更新助手、自启动入口也由此协调。
- `httpserver` 负责参数解析、访问策略、状态码、JSON 和事件输出，通过组件 API 完成业务操作。
- 存储与更新组件返回数据和可识别的错误，不依赖 HTTP handler、`ResponseWriter` 或整个 `server`。更新下载使用 HTTP 客户端属于其外部服务访问职责。
- 组件拥有保护自身一致性的锁和可变状态；锁随数据一起迁移，避免 HTTP 层和组件分别保护同一份数据。
- 传输登记、停止接收新传输与关停确认共用同一状态源。SSE 订阅由 HTTP 层管理，并响应应用取消。跨组件通知通过小型回调或事件传递，避免循环依赖。
- 接口由调用方按实际需求定义；可以直接使用具体类型，不为每个结构体机械创建接口。

## 分阶段实施

### 阶段一：原包内梳理

将 `main.go` 中的路由、事件、文件 handler、网络探测与启动代码拆到职责明确的文件，保持 `package main` 与行为不变。标记共享状态、跨文件依赖及恢复顺序，为后续提包建立边界。

验收：原有入口、路由、资源嵌入与测试行为保持一致。本阶段只是准备工作，不以减少单文件行数作为完成整个优化的标准。

### 阶段二：提取独立组件

按依赖情况逐个提取 `textstore`、`desktop`、`updater`，HTTP handler 暂留原包并调用新组件。

- 文本存储包含读写、备份、恢复及相关并发保护，维持已有数据格式与限制。
- 桌面能力保留平台构建约束和不支持平台的明确行为。
- 更新服务接收版本、公钥与启动配置，保留验签、平台检查、健康探测、回滚和子进程参数语义。

验收：组件可脱离原 `server` 测试；原 HTTP 行为及平台行为兼容。每提取一个组件就完成相关验证。

### 阶段三：提取文件存储

将共享路径解析、名称校验、冲突处理、文件操作、上传提交、回滚和启动恢复统一归入 `filestore`。

- 恢复逻辑不再通过构造 HTTP `server` 使用路径能力。
- 文件变更共用路径策略和一致性保护；HTTP 层只处理请求与响应。
- 保持上传接收与提交的事务边界、取消规则、数据目录位置和崩溃恢复语义，不因拆包增加数据迁移。

验收：目录操作、上传冲突、替换失败、回滚与重启恢复等现有测试仍覆盖相同行为，锁边界清晰。

### 阶段四：收拢入口与 HTTP 层

将剩余路由和 handler 迁入 `httpserver`，将应用组装、启动和关停协调迁入 `app`。根目录留下薄入口与资源嵌入。

验收：根目录入口不包含业务 handler 或持久化逻辑；所有内部包依赖单向，测试与实现相邻。同步更新开发文档中的代码位置和构建说明。

## 构建与兼容性处理

1. **资源嵌入：** 根目录 `assets.go` 保留 `//go:embed web/*`，通过 `fs.Sub` 获得前端根目录，以 `fs.FS` 传入应用。嵌入模式不支持 `..`，不能在 `internal` 中使用 `../../web`。
2. **构建变量：** 将 `version`、`updatePublicKey` 留在根目录 `main` 包，通过配置传递，兼容 `-X main.version=...` 和 `-X main.updatePublicKey=...`。同步调整原先直接修改全局变量的测试。
3. **构建输入：** Dockerfile 当前只复制根目录 Go 文件，需加入 `internal/`；Makefile 的源文件收集需覆盖子包，检查发布脚本和 CI 是否仍覆盖全部构建输入。
4. **测试运行目录：** 更新测试会执行 `go build .`。测试迁入子包后，须显式定位模块根目录并设置构建工作目录，构建真实主程序；不要依赖测试进程的默认目录。
5. **更新身份兼容：** 当前更新校验检查可执行文件的 `buildinfo.Path == "lan-copy"`。本计划保留模块路径和根入口；未来移动到 `cmd/lan-copy` 或变更 module 路径时，必须单独设计新旧版本更新兼容方案。
6. **工具位置：** 保留 `scripts/update-manifest`。出现更多面向用户的命令后再评估 `cmd/`，迁移时同步处理安装路径、发布脚本与更新身份校验。

## 验证与完成标准

- 每个阶段保持可独立审查、可编译、可运行，避免同时进行目录重构与功能变更。
- 运行受影响包的测试；阶段完成后运行现有 `make test` 和 `go vet ./...`，需要时针对共享状态运行竞态检查。
- 验证 Windows、macOS、Linux 的构建；交叉编译只证明可编译，自启动、控制台和更新重启需在对应平台验证实际行为。
- 验证 `go run .`、`go build .`、Docker 构建及既有发布打包流程，确认版本、公钥、静态资源和更新身份正确。
- 保持 HTTP 路由、响应、访问权限、命令行参数、存储格式及恢复行为兼容。补充测试用于验证真实的边界和行为风险，不为纯文件搬迁新增重复测试。
- 最终按职责内聚、依赖单向、状态归属和独立可测性验收，不按目录数量验收。

## 范围约束

本计划不引入 `pkg/`、多 module、通用 `utils` 包或统一的 controller/service/repository 分层，不为整理目录引入第三方框架、数据库或公开库 API。确有复用或产品需求时另行评估。
