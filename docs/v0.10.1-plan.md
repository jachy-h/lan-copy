# Lan Copy v0.10.1 Podman 兼容计划

更新日期：2026-11-19。状态：**已批准并完成实现，自动化验证通过，待真实 Podman 人工验收**。

## 背景与目标

插件服务目前固定按 Docker 连接：`dockerruntime.New` 只使用 `client.FromEnv`，默认 `unix:///var/run/docker.sock`；页面与文档也把运行时写死为 Docker。

Podman 提供了 Docker Engine API 兼容层（`podman.sock`），因此同一套 Docker SDK 代码可以复用，不需要引入第二套客户端。问题是**端点**和少数**引擎差异**：

- Linux rootful：`unix:///run/podman/podman.sock`
- Linux rootless：`unix://$XDG_RUNTIME_DIR/podman/podman.sock`（通常是 `/run/user/<uid>/podman/podman.sock`）
- macOS/Windows：`podman machine` 转发出的 socket / named pipe
- Docker：`/var/run/docker.sock`、Docker Desktop、OrbStack、Windows named pipe

本版目标：

1. 启动插件管理前检测环境里可用的容器运行时，Docker 与 Podman 都能连接。
2. 不执行 `docker` / `podman` 命令行，继续只走 Engine API（沿用 v0.8.0 已批准的设计约束）。
3. 无运行时/不可用时保持现状：主程序正常启动，插件页显示不可用原因。
4. 按实际引擎做正确的最小差异处理，并在页面与文档中明确显示 Docker 或 Podman。

## 已确认的边界

- 只做“本机容器运行时”自动发现，不做远程 `tcp://`、TLS、SSH 连接的管理界面；仍可通过环境变量显式指定。
- Podman 走 Docker 兼容 API，不引入 Podman REST 专有字段，也不新增 Podman Go SDK。
- 不改变现有插件镜像、Manifest、生命周期事件、智能表格 API、数据目录与恢复语义。
- 镜像导入继续使用 `docker save` / `podman save` 生成的标准 tar/tar.gz。

## 非目标

- 不实现 registry 拉取（`PullImage` 仍为未实现）。
- 不自动安装或启动 Docker/Podman，不管理 `podman machine` 生命周期。
- 不支持 Linux rootless Podman 下宿主机目录 UID 映射的自动修正（见“已知限制”）。
- 不改前端整体视觉，只改运行时名称与提示文案。

## 一、运行时检测

新增 `internal/plugin/dockerruntime/detect.go`，以及平台候选列表文件 `detect_unix.go`、`detect_windows.go`（沿用包内文件名后缀约定）。

```go
type Detected struct {
    Type       string // "docker" | "podman"
    Host       string // 传给 Docker SDK 的端点
    Version    string
    APIVersion string
    OS, Arch   string
    Source     string // 环境变量名或 socket 路径，便于日志与页面诊断
}

func Detect(ctx context.Context) (Detected, error)
```

### 1.1 候选顺序

| 顺序 | 候选 | 说明 |
| --- | --- | --- |
| 1 | `DOCKER_HOST` | 显式指定；Docker 习惯变量，也常用于把 Podman socket 暴露给 Docker 工具 |
| 2 | `CONTAINER_HOST` | 显式指定；Podman 习惯变量 |
| 3 | Docker socket | `/var/run/docker.sock`、`/run/docker.sock` |
| 4 | Podman 本机 socket | `/run/podman/podman.sock`、`$XDG_RUNTIME_DIR/podman/podman.sock`、`/run/user/<uid>/podman/podman.sock` |
| 5 | Podman machine socket | `$HOME/.local/share/containers/podman/machine/podman.sock`，以及该目录下一层的 `*/podman.sock` |
| 6 | Windows named pipe | `//./pipe/docker_engine`、`//./pipe/podman-machine-default` |
| 7 | SDK 默认端点 | 兜底；主要让 `Info` 返回不可用原因 |

规则：

- 只要 `DOCKER_HOST` 或 `CONTAINER_HOST` 存在，就**只使用该端点**，失败不静默切到其他引擎，避免装错环境后误操作另一套容器。
- 没有环境变量时按上表探测；每个候选先 `Ping` 再 `ServerVersion`，成功即停止。
- 未被使用的候选路径不存在时快速跳过；每次探测 1.5s 超时，整个检测 4s 上限，避免拖慢启动。
- 所有候选都失败时返回 `plugin.ErrRuntimeUnavailable` 包装错误；`preparePlugins` 记录日志但仍创建 Manager，页面显示“不可用”，主程序不受影响。

### 1.2 引擎识别

`ServerVersion` 的兼容返回差异：

- Docker：`Components[].Name` 为 `Engine`，`Platform.Name` 含 `Docker`。
- Podman：`Components[].Name` 为 `Podman Engine`，`Platform.Name` 为宿主机平台。

因此识别规则：`Components` 或 `Platform.Name` 中出现 `podman`（不区分大小写）即判为 `podman`，否则 `docker`。识别逻辑放在纯函数 `engineType(version)` 中，便于单元测试。

## 二、运行时差异处理

### 2.1 类型贯通

- `dockerruntime.Options` 增加 `Type string`；`Runtime` 保存检测结果，`Info()` 返回 `Type: "docker" | "podman"`，并在每次 `Info` 时按 `/version` 重新校准，避免检测后引擎被替换。
- `app.preparePlugins` 先调用 `Detect`，把 `Type` 同时传给 Runtime 与 Manager 的 `RuntimeSettings`；`Instance.RuntimeType` 因此记录真实引擎。
- 检测失败时 `Type` 回落到 `docker`，保持现有状态文件与页面行为兼容。

### 2.2 loopback 模式访问宿主机 API

| 引擎 | 容器内主机名 | ExtraHosts |
| --- | --- | --- |
| Docker | `host.docker.internal` | `host.docker.internal:host-gateway`（现状） |
| Podman | `host.containers.internal` | `host.containers.internal:host-gateway` |

- `pluginExtraHosts(networkMode, runtimeType)` 按引擎选择固定映射；`container` 模式仍为空。
- `dockerruntime/convert.go` 的允许列表从单一值改为上述两个固定值，仍然拒绝任意 ExtraHosts。
- `-plugin-api-url` 显式指定时优先级不变；未指定时由 `preparePlugins` 按“网络模式 + 检测到的引擎”推断：`container` → `http://lan-copy:<端口>`，`loopback` → 对应引擎的主机名。
- 已安装实例保存的是安装时的地址与 ExtraHosts，切换引擎后需要卸载重装才能换用新主机名；页面与文档注明。

### 2.3 拒绝挂载运行时 socket

现有代码只拒绝 `docker.sock`。Podman 场景下 `podman.sock` 同样等于宿主控制权，必须在两处补上：

- `plugin.PrepareHostMount`：拒绝 `docker.sock` 与 `podman.sock`。
- `dockerruntime.buildCreateConfigs`：同样拒绝两种 socket。

### 2.4 兼容性核对

同一套 SDK 调用在 Podman 兼容 API 下的既有行为（本次只做验证与必要适配，不扩大改动）：

| 能力 | Podman 兼容 API | 处理 |
| --- | --- | --- |
| `_ping` / `/version` / API 版本协商 | 支持 | 直接使用 |
| `/images/load` 流式导入 | 支持，输出同为 `Loaded image:` | 现有解析复用 |
| 用户自定义 bridge 网络 | 支持（netavark） | 现有 `EnsureNetwork` 复用 |
| 创建/启停/重启/删除/Inspect | 支持 | 复用 |
| `ExtraHosts` | 4.x 起支持 `host-gateway` | 使用固定映射 |
| `Init`、只读根、`CapDrop ALL`、`no-new-privileges`、tmpfs、`pids_limit`、内存/CPU 限制 | 支持 | 复用 |
| `LogConfig: json-file` | 支持（映射为 k8s-file） | 复用 |
| 日志多路复用、Stats | 支持；`precpu_stats` 可能为空 | CPU 计算已有零值保护，复用 |
| 端口回环发布 | 支持 | 复用 |

如真实 Podman 验证发现某项不兼容，只在该适配层做最小降级，并在进度文档记录，不引入 CLI 调用。

## 五、验收清单

1. 仅有 Docker：行为与 v0.10.0 一致，页面显示 Docker。
2. 仅有 Podman（rootful 或 machine）：页面显示 Podman；导入镜像、安装、启动、健康检查、日志、停止、卸载全部可用；插件可通过 `LAN_COPY_API_URL` 访问宿主机表格 API。

5. 环境变量指向不可达端点：明确报不可用，不静默改用本机另一引擎。
6. 挂载 `docker.sock` 或 `podman.sock` 均被拒绝。

## 六、修订 1：目标机器 Podman 不可用

目标部署机器安装 Podman 后页面仍显示不可用。Podman 安装后 Docker 兼容 API 的 socket 未必已启用，而页面错误固定为“无法连接 Docker Engine”，且探测结果未回显，无法判断是 socket 未启动、路径未命中还是 `DOCKER_HOST` 指向失效端点。因此补充：

- 探测失败返回结构化 `DetectError`：列出已尝试的端点；检测到已安装 Podman 时提示启用 `podman.socket` 的具体命令；显式环境变量失效时提示可删除变量改为自动检测。
- 探测错误通过 `Runtime.Info` 显示到页面；每个端点的原始连接错误写入启动日志。
- 扩大候选：`/var/run/podman/podman.sock`、`$TMPDIR/podman/podman.sock`，root 运行时扫描 `/run/user/*/podman/podman.sock`。
- `friendlyRuntimeError` 不再只提 Docker：有诊断详情时直接显示，否则给出 Docker/Podman 通用排查提示。

## 七、修订 2：检测阶段自动启动 Podman socket（已批准：只 start）

目标：不再要求用户在目标机器上手动执行 `systemctl enable --now podman.socket`，由 Lan Copy 在运行时检测失败后自动拉起 Podman 的 Docker 兼容 API，然后重新探测。

### 触发条件（全部满足）

1. 没有设置 `DOCKER_HOST` / `CONTAINER_HOST`（显式端点保持权威，不做隐式干预）。
2. 所有自动候选端点探测失败。
3. `podman` 可执行文件存在。
4. 运行平台为 Linux 且有 `systemctl`。
5. 未设置 `LAN_COPY_DISABLE_PODMAN_AUTOSTART=1`。

### 行为

- 非 root：执行固定参数 `systemctl --user start podman.socket`。
- root：执行固定参数 `systemctl start podman.socket`（rootful）。
- 只 `start`，不 `enable`：不修改开机自启等持久化配置；每次启动检测失败时再尝试一次。
- 不经过 shell、不接受用户输入；命令超时 3 秒。
- 启动后在约 2 秒内轮询重试 Podman 候选端点，成功则继续使用检测结果。
- 成功/失败都写入启动日志；失败时保留现有页面提示和原始错误详情。
- 新增环境变量 `LAN_COPY_DISABLE_PODMAN_AUTOSTART=1` 可完全关闭该行为。
- 同时安装 Docker 与 Podman、且 Docker 未运行时，自动启动 Podman 后会使用 Podman；页面与启动日志显示实际引擎，可用上述开关关闭。

### 不自动处理的场景

- macOS / Windows 的 `podman machine`：启动 machine 耗时长且属于 `podman` CLI 操作，仍提示用户手动 `podman machine start` 或用 `DOCKER_HOST` 指定。
- 无 systemd 的 Linux（容器内、WSL1、非 systemd 发行版）：保持提示。
- root 运行但目标是某个普通用户的 rootless socket：root 启动的是 rootful 服务，存储与用户 rootless 独立；需要时仍用 `DOCKER_HOST` 指向该用户 socket。
- rootless 用户会话不可用（无 `XDG_RUNTIME_DIR` / D-Bus，例如 headless SSH 未开 lingering）：保持提示。

### 风险与测试

- 自动启动系统服务是新的副作用；仅限固定单元、固定参数、只 start 不 enable，并且可关闭。
- 测试：假激活器覆盖“激活后重试成功”“激活失败回退”“显式环境变量不触发”“关闭开关不触发”；平台相关命令构建在 linux 文件中，其他平台为空实现。
- 真实环境：Linux rootless 与 rootful 各验证一次；本机 Docker 回归不受影响。

## 八、修订 3：插件页“启动 Podman”按钮（已批准：允许局域网设备）

目标：运行时不可用时，页面直接提供“启动 Podman”按钮；点击后在后台拉起 Podman API，页面无需重启 Lan Copy 即可恢复。

### 接口与权限

- `GET /api/plugins/runtime` 新增 `startAvailable`：仅当自动探测失败、未设置 `DOCKER_HOST`/`CONTAINER_HOST`、本机存在 podman 且平台支持启动时为 true。前端据此显示按钮。
- 新增 `POST /api/plugins/runtime/start`：
  - 要求同源 + `X-Lan-Copy-Action: plugins`；按用户确认，**允许局域网设备调用**。任何能访问插件页的设备都可触发宿主机启动 Podman，文档明确提示该风险。
  - 复用现有异步任务：返回 `202 + taskId`，前端用现有 `waitForTask` 展示进度。
  - 已可用、平台不支持或重复点击都作为任务失败返回：HTTP 先返回 `202 + taskId`，原因写在任务错误里。
- 启动命令仍为固定参数、无 shell、无用户输入：
  - Linux：`systemctl --user start podman.socket`（root 为 `systemctl start podman.socket`）。
  - Windows / macOS：`podman machine start`（podman 可执行文件路径来自 PATH 或常见安装目录）。
  - 命令超时 90 秒；随后最多约 30 秒轮询 Podman 端点。

### 启动后即时生效

- `dockerruntime.Runtime` 增加 `StartRuntime(ctx, progress)`：拉起服务后重新 `Detect`，成功后原子替换内部 Docker 客户端与运行时类型，清除启动探测错误；失败保留原错误。
- `plugin.Runtime` 接口不变，使用可选能力接口 `interface{ StartRuntime(...) error }`，fake/测试实现不受影响。
- 运行时类型改为可在运行中更新：Manager 保存原子值，`Instance.RuntimeType` 与 ExtraHosts 使用最新类型。
- `LAN_COPY_API_URL` 改为安装时按“网络模式 + 端口 + 当前类型”计算，`-plugin-api-url` 显式值保持最高优先级；避免从 Docker 切到 Podman 后仍注入 `host.docker.internal`。
- 页面点击后成功后自动 `refresh`，插件列表、镜像与运行时状态一起更新。

### 页面

- 不可用横幅内增加按钮：`启动 Podman`；启动中显示“正在启动 Podman…”并禁用；失败在现有任务错误区域显示。
- 按钮只在 `startAvailable === true` 时出现，不改变现有 Docker 正常路径。
- 仍保留自动启动（Linux）与手动 `DOCKER_HOST` 两种方式，按钮是第三种显式入口。

### 测试与验收

- 单元：`startAvailable` 计算（显式环境变量/无 podman/不支持平台为 false）；启动成功后客户端替换与类型更新；启动失败保留错误与 409/501 映射；`defaultAPIBaseURL` 随类型变化。
- HTTP：局域网 + 动作头可调用、缺少动作头 403、GET 405；启动失败通过任务状态返回（已可用/不支持/重复）。
- 前端：按钮显示条件、点击调用、进度/失败提示、成功后刷新。
- 真实环境：Windows `podman machine start` 与 Linux rootless/rootful 各一次；Docker 回归不受影响。

### 风险

- 启动系统服务/虚拟机属于高权限副作用；按确认结果允许局域网设备调用，仅靠同源 + 动作头防护，需只部署在可信局域网。
- Windows `podman machine start` 首次可能超过 30 秒，任务期间页面可继续使用；超时后给出日志。
- 切换引擎后旧引擎里的插件容器不会迁移；页面以当前引擎状态为准。

## 九、已知限制与风险

- **Linux rootless Podman**：容器进程 UID 经 subuid 映射，写挂载目录时可能没有权限。建议使用 rootful socket 或 `podman machine`；本版只做文档说明，不自动 chown，避免破坏 Lan Copy 自身对数据目录的访问。
- **macOS/Windows Podman**：宿主机目录必须在 `podman machine` 共享路径内；默认数据目录在用户主目录下，通常已覆盖。
- **旧版 Podman**：低于 4.1 可能不支持 `host-gateway`；检测本身可用，但 loopback 访问宿主机 API 会失败，文档给出升级建议。
- **检测成本**：候选 socket 全部不存在时，主要为本地连接失败，预计 < 1s；最坏情况受 4s 总超时约束。
- 本机当前只安装了 Docker，Podman 真实链路需要人工安装后验收；自动化测试以假 Engine + 候选/识别逻辑为主。
