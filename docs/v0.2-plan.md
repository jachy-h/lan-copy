# Lan Copy v0.2 架构优化计划

## 背景与原则

当前项目采用 Go 单二进制、嵌入式前端和本地文件系统存储，部署简单，适合局域网内临时共享。v0.2 延续这一部署方式，优先修复并发操作中的正确性和数据恢复问题，再梳理服务边界与资源管理。当前已有的路径检查、上传暂存、更新包签名和更新回滚机制作为后续改进的基础。

本文中的 P1 表示应优先处理的正确性、可靠性问题；P2 表示可分阶段实施的结构、性能和测试改进。实现时应为每项补充相应回归测试，并确认 Windows、macOS 和 Linux 行为一致。

## P1：正确性与可靠性

### 1. 收敛全局锁的范围

**现状：** `server.mu` 同时保护文件操作和文本存储。目录遍历、搜索、排序以及 HTTP 响应写出可能占用这把锁；名称冲突处理也在锁内执行。`availableName` 对权限错误等非“文件不存在”错误没有退出条件，可能持续重试并阻塞共享空间的其他操作。

**目标：** 缩短临界区，避免慢磁盘操作和慢客户端阻塞无关请求。名称冲突处理须有明确的错误返回和有限重试次数。

**建议：** 先调整 `availableName`，只在目标确实不存在时返回候选名称，对其他错误直接返回；随后将文件操作与文本存储分锁。检查目标和执行提交时仍需保留必要的并发保护。尽可能先在锁内取得一致的元数据快照，再在锁外排序和写 HTTP 响应。为递归查询增加上下文取消、结果数或遍历预算。

**代码位置：** `main.go` 的 `listFiles`、`savePartTo`、`availableName`；`filesystem.go` 的 `listDirectory`；`text.go` 的文本读写处理。

### 2. 统一上传流程和失败恢复

**现状：** `/api/upload` 按文件逐个写入最终目录。批次后续失败时，服务按路径清理先前写入的文件；并发移动、删除或替换可能使清理对象发生变化。`/api/upload-tree` 使用暂存目录与备份目录，但顶层条目通过多次改名提交，进程在提交过程中退出时没有启动恢复流程。

**目标：** 两种上传方式共享校验、冲突处理、暂存、提交和失败清理逻辑；部分失败不会悄悄留下半批文件或丢失原文件。

**建议：** 将上传处理抽为服务层，普通上传和目录上传只负责解析各自的请求格式。提交操作应持有稳定的目标引用或提交标识，避免按可变路径回滚。为替换备份记录提交阶段，并在启动时识别未完成记录，自动恢复原内容或继续清理。若无法实现跨多个文件的文件系统原子提交，应明确事务边界并保证崩溃后可恢复。

**代码位置：** `main.go` 的 `uploadFiles`、`savePartTo`、`cleanupFiles`；`upload_tree.go` 的 `uploadTree`、`commitUploadTree`。

### 3. 统一关停、更新与在途请求管理

**现状：** 网页关停和更新通过 `shutdownRequested` 发起关闭，HTTP 服务器有 5 秒关停期限，之后可能强制关闭连接。SSE 处理器只等待请求上下文，不直接响应应用关停。进程入口也没有把系统退出信号纳入同一生命周期流程。

**目标：** 关停或更新时停止接收新写入，结束实时订阅，等待正在提交的文件操作完成，再关闭 HTTP 服务；等待超时应有可诊断的处理结果。

**建议：** 增加应用级 context 和统一的生命周期协调器。SSE 同时监听应用 context 与请求 context；上传和更新提交阶段使用可取消的请求上下文，并区分可中断的接收阶段与必须完成或回滚的提交阶段。通过系统信号触发相同的关停路径，更新重启复用该流程。

**代码位置：** `main.go` 的 `fileEvents`、`handleShutdown`、`main`；`update.go` 的 `installUpdatePackage`。

### 4. 统一路径策略并隔离内部数据

**现状：** 名称与路径规则分布在 `safeName`、`sharedPath`、目录操作和树上传校验中。内部文件前缀的大小写处理存在差异；普通上传和树上传对保留名称的规则不完全相同。基于 `Lstat` 检查后再按路径打开，也无法约束共享目录被其他本机进程并发修改的情况。

**目标：** 所有文件入口使用相同的命名、保留名称、大小写和组件规则；应用内部数据不暴露在用户共享空间的命名边界中。明确本机外部进程直接修改共享目录是否属于支持场景。

**建议：** 提供单一的路径解析与验证实现，供上传、预览、下载、移动和删除复用；补充 Windows/macOS 大小写不敏感文件系统的测试。评估将文本数据库、上传暂存和恢复记录放到共享目录之外的应用数据目录。对于外部并发改动，优先使用平台支持的基于目录句柄的安全文件操作；若暂不支持，明确运行约束并避免把路径预检描述成对抗本机修改的安全边界。

**代码位置：** `main.go` 的 `safeName`、`serveSharedFile`；`filesystem.go` 的 `sharedPath`、`mutateDirectory`；`upload_tree.go` 的 `validateUploadTree`。

### 5. 修复文本存储替换窗口并设置容量边界

**现状：** 文本内容存储在单个 JSON 文件中，每次新增或删除都要读取、解析并重写整个文件。目前没有条数或总存储量限制。跨平台替换失败的回退路径会先删除旧文件，再尝试把临时文件改名；第二次改名若失败，原文本库会丢失。

**目标：** 更新失败时保留旧数据，并为文本存储提供明确的容量与保留策略。

**建议：** 先调整替换流程，确保在新文件成功落位前旧文件始终可恢复，并检查必要的写入、关闭和同步错误。增加文本条数或总容量上限；是否增加过期清理由产品保留策略决定。当前数据规模较小时可继续使用 JSON；当容量或并发需求达到限制后，再评估迁移 SQLite。

**代码位置：** `text.go` 的 `readTextsLocked`、`writeTextsLocked`、`createText`、`deleteText`。

## P2：边界、性能与维护性

### 6. 为上传增加全局资源预算和冲突预检

**现状：** 上传限制按单请求执行，缺少进程级并发数、暂存空间和空闲超时限制。目录上传会先传完全部数据，再检查目标冲突；用户确认替换后需要重新传输整个批次。

**目标：** 控制多个并发上传对磁盘和连接的占用，并尽早反馈冲突，减少大文件重复传输。

**建议：** 为并发上传设置信号量，为暂存空间设置预算，并为请求读取设置空闲超时。可将目录上传演进为两阶段协议：先提交清单并返回冲突与上传会话，再上传内容并提交；最终提交时仍须重新检查目标，避免预检与提交之间的竞争。断点续传和分块上传应根据真实使用需求单独评估。

**代码位置：** `main.go` 的上传处理；`upload_tree.go` 的 `uploadTree`；`web/filesystem.js` 的目录上传重试流程。

### 7. 按职责划分内部模块

**现状：** HTTP 路由、请求处理、文件系统操作、共享锁和平台能力集中在 `main` 包。处理器直接编排 I/O、错误映射和事件通知，增加回收站、权限或上传恢复时容易重复实现边界逻辑。

**目标：** 保持单进程与单二进制部署，同时让核心操作可独立验证、职责清楚。

**建议：** 按需求逐步建立 HTTP、文件与上传服务、文本存储、应用生命周期、事件通知等内部边界。HTTP 层处理参数解析和状态码；服务层负责路径、冲突、提交和恢复；存储层负责持久化。不要仅为目录结构拆分而引入不必要的接口或第三方依赖。集中定义访问策略，并记录各 API 对局域网访客和本机用户的权限差异。

**代码位置：** `main.go`、`filesystem.go`、`upload_tree.go`、`text.go`、`update.go`、`autostart.go`。

### 8. 统一变更通知和前端请求取消

**现状：** 文件更新由 SSE 通知，通知后客户端重新请求完整目录；文本通过 60 秒轮询刷新。目录请求使用递增序号丢弃过期响应，但旧请求仍会继续占用服务端资源。

**目标：** 避免无意义的重复目录扫描与响应，并在切换目录、关闭页面或服务关停时终止不再需要的工作。

**建议：** 统一文件和文本变更事件格式，按需支持目录范围或版本号。前端对搜索输入和目录切换使用 `AbortController` 取消旧请求；对连续事件做短时间合并，减少重复刷新。保留必要的低频轮询作为 SSE 断线后的恢复机制，并在页面隐藏时暂停不必要的轮询。

**代码位置：** `main.go` 的 `fileEvents`、`notifyFilesChanged`；`web/filesystem.js` 的 `loadDirectory`；`web/app.js` 的文本刷新逻辑。

### 9. 统一测试入口并减少脆弱的前端测试

**现状：** Go 测试覆盖文件系统、上传、预览和更新等主要功能。部分前端脚本通过截取源码片段后在虚拟机中执行，函数间依赖变化时容易失效。`make test` 不包含这些前端检查；CI 当前也没有运行 `scripts/test-dialog.cjs`。

**目标：** 本地与 CI 使用一致的验证入口，测试稳定覆盖实际前端行为，并让失败能定位到具体模块。

**建议：** 汇总 Go、Python 和 Node 测试命令到一个仓库入口，并由 CI 调用。补齐对话框测试的 CI 执行。逐步将前端逻辑拆为可独立导入的模块，或使用真实 DOM 环境验证关键交互，减少依赖字符串切片的测试。跨平台验证路径规则、原子改名与更新恢复时，继续使用平台矩阵。

**代码位置：** `Makefile` 的 `test` 目标；`.github/workflows/release.yml`；`scripts/test-*.cjs`。

## 建议实施顺序

1. 修复 `availableName` 的错误处理和有限重试，补充异常文件名及权限错误测试。
2. 修复文本存储替换失败时的旧数据保护，并明确文本容量上限。
3. 统一上传服务，先保证上传失败和替换失败后的清理与恢复，再处理进程崩溃恢复。
4. 缩小共享锁范围，并为关停、SSE、上传提交和更新建立统一生命周期。
5. 统一路径验证和内部数据布局，完善跨平台路径测试。
6. 按实际负载推进上传资源预算、事件刷新优化和内部模块拆分。
7. 收敛本地与 CI 测试入口，逐步替换脆弱的前端片段测试。

## 验收标准

- 非预期的文件系统错误会及时返回，不会造成无限重试或长期占用全局锁。
- 批量上传在请求失败、提交失败和服务重启后，目标内容及原有内容均处于可解释、可恢复的状态。
- 文本替换失败不会删除最后一份有效数据；文本规模有明确上限或保留策略。
- 关停与更新能通知 SSE 退出，并按约定处理在途上传和提交操作。
- 所有入口共用路径规则，在 Windows、macOS 和 Linux 测试中表现一致。
- CI 与开发文档提供一致的测试入口，关键前端交互测试稳定运行。
