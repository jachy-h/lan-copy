# 在线与离线更新

两个主页面的分享按钮左侧都有设置齿轮，弹窗包含“关于”和“更新”。拖入一个发布包即开始上传、校验、替换和重启；也可以点击上传区域选择文件。更新期间请等待其他文件传输完成。程序目录必须可写，无需管理员权限。

支持通过 localhost、局域网 IPv4/IPv6 地址或本地域名打开页面并更新，包括其他局域网设备。更新权限不依赖连接来源 IP，而依赖程序内置的可信公钥：所有包必须通过 Ed25519 验签，未配置或配置无效公钥时禁用更新。仍检查 Origin、Fetch Metadata 和自定义操作头，拒绝跨站浏览器请求。需要关闭更新时可设置 `LAN_COPY_DISABLE_UPDATE=1`。Docker 镜像已默认禁用；开发用的 `go run` 临时程序也禁用。首次使用此功能需手动运行包含更新功能的程序。

## 检查 GitHub 新版本

进入“更新”菜单会由运行 Lan Copy 的电脑访问 GitHub 最新正式 Release，并按 `主版本.次版本.修订号` 比较版本号，兼容标签的 `v` 前缀。结果在服务端缓存 5 分钟，重新进入菜单或点击“重新检查”会读取缓存或发起检查。开发版 `dev` 不自动比较或安装线上版本。

发现新版本后提供“下载并更新”和“前往查看”。下载使用运行程序的系统与架构（而非浏览器设备），支持 Windows amd64 和 macOS Apple Silicon。程序会下载完整 Release 附件，复用离线上传的暂存、大小限制、Ed25519 验签、平台和程序校验、安装重启、失败恢复及页面刷新流程；同时要求包内版本与 Release 标签一致。无适用附件或当前启动方式不支持更新时，禁用安装并说明原因，仍可查看 Release。

检查或下载 GitHub 失败时可重试，或继续使用拖入压缩包的离线更新。检查超时为 12 秒，下载请求最长 5 分钟；不会自动安装或重启，需用户点击“下载并更新”。

## 构建更新包

```sh
make build
```

默认自动读取项目的 `.config/update.key` 私钥和 `.config/update.pub` 公钥，不需要手动 export。此目录已被 Git 忽略，不会包含在发布包中。CI 仍可通过 `LAN_COPY_SIGNING_KEY` 环境变量和 `UPDATE_PUBLIC_KEY` 参数覆盖本地密钥。自定义文件位置可设置 `UPDATE_SIGNING_KEY_FILE` 和 `UPDATE_PUBLIC_KEY_FILE`。Windows ZIP 和 macOS tar.gz 包中会包含程序、`update.json` 和 `update.sig`。`make build` 从项目根目录的 `VERSION` 读取上次成功版本，自动增加 patch（初始基线 `0.1.0`，首次自动构建为 `0.1.1`）。所有平台使用同一个新版本，全部打包成功后才写回 `VERSION`；构建失败不递增。构建结束打印版本、完成时间、耗时、签名方式及产物绝对路径和大小。可用 `make build VERSION=1.2.3` 指定版本，成功后也将其保存为下次自动递增的基线。请将 `VERSION` 随发布代码一起提交。直接执行 `make windows`、`make macos` 或 `make artifacts` 使用已保存版本，不自动递增。程序版本通过 `-X main.version=1.2.3` 写入；直接 `go build` 未指定时仍为 `dev`。Make 每次重新生成发布包，防止更换版本或公钥后复用旧包。Windows Authenticode 签名流程 `scripts/release-windows.ps1 -Version 1.2.3` 同样生成清单，清单校验的是最终签名后的程序。

清单格式：

```json
{
  "app": "lan-copy",
  "version": "1.2.3",
  "os": "windows",
  "arch": "amd64",
  "binary": "lan-copy.exe",
  "sha256": "可执行文件的 SHA-256 小写十六进制值"
}
```

包内支持一个顶层文件夹；只提取已知文件，不将归档路径直接写入磁盘。校验系统、架构、SHA-256、Go 可执行程序的模块路径与平台，并拒绝重复目标、特殊文件和非法路径。上传及解压总大小上限为 128 MiB，最多 256 个归档条目。旧发布包没有清单，无法直接使用。更新不限制版本号升降，文件内容相同的程序会被拒绝。

## 固定发布签名公钥

在受信环境生成专用于更新包的 Ed25519 密钥（与 Windows 代码签名证书分开）。基础版和后续更新版都必须固定同一可信公钥；私钥仅用于发布签名，不放入程序：

```sh
mkdir -p .config
go run ./scripts/update-manifest -generate-key .config/update.key
```

命令以独占方式创建权限为 0600 的私钥文件，向标准输出打印 Base64 公钥，将输出的公钥保存到 `.config/update.pub`。私钥不要放入仓库或发布包。将私钥内容作为 CI 的 `LAN_COPY_SIGNING_KEY` 秘密环境变量，构建时传入公钥：

```sh
make artifacts VERSION=1.2.3 UPDATE_PUBLIC_KEY='<上一步输出的 Base64 公钥>'
```

打包工具要求配置可信公钥，以及对应的私钥文件或 `LAN_COPY_SIGNING_KEY` 环境变量（环境变量优先），会对 **update.json 原始字节** 签名，并写出 Base64 `update.sig`。缺少公钥、私钥或密钥不匹配时，拒绝生成发布包；程序更新时必须验证签名，不能通过上传无签名包绕过。之后的发布应继续固定同一公钥；更换公钥需要设计受信迁移流程或手动替换程序。

Windows PowerShell 发布流程使用 `LAN_COPY_UPDATE_PUBLIC_KEY` 环境变量或 `-UpdatePublicKey` 参数，以及同样的 `LAN_COPY_SIGNING_KEY` 秘密环境变量。清单签名在 Authenticode 签名之后生成。

## 替换与失败恢复

1. 在当前可执行文件的目录内创建随机临时目录，保存上传包与校验后的候选程序。校验失败不退出服务。
2. 复制当前可信程序作为临时辅助进程，并等待它就绪。该进程脱离原进程的控制台/会话；不执行更新包中的任何辅助脚本。
3. 返回更新标识，旧服务尝试优雅退出（最多 5 秒）；辅助进程等待旧进程结束，备份旧程序，再替换可执行文件。
4. 使用原参数、原工作目录和明确的监听地址、共享目录启动新程序。重启不额外打开浏览器或等待控制台按键。
5. 通过回环 HTTP 检查新进程的随机更新标识（最多 25 秒），不以旧服务仍可访问判断成功。成功后删除旧程序备份；浏览器确认标识后刷新。
6. 新进程启动或就绪检查失败时，停止新进程、恢复并重启旧程序。页面识别恢复标识并显示失败提示，不把恢复当作更新成功。

程序目录中的 `lan-copy-update.log` 记录最近一次辅助更新结果。Windows 无法删除正在执行的辅助程序，因此成功后会保留只包含辅助程序的 `.lan-copy-update-*` 目录；服务恢复后可手动删除。失败时保留临时目录及诊断信息；如果恢复也失败，日志记录备份位置，可手动恢复。断电或系统强制终止不保证自动恢复。

## GitHub 自动构建

代码提交后，可在 `main` 上执行 `make publish`，自动完成签名构建、版本递增、版本提交、标签和推送；有未提交文件时会停止并提示先 commit。最终 Release 由 GitHub Actions 测试通过后发布。

推送 `main` 自动测试和构建，推送版本标签后发布 Release。CI 需要一次性配置与本地相同的签名密钥，使用已提交的 `VERSION` 且不递增。详见 [GitHub 自动构建与发布](GITHUB-ACTIONS.md)。

## 验证

`go test ./...` 包含压缩包、强制签名、局域网更新和跨站请求限制测试，并在当前系统上构建和启动真实程序，验证更新成功、启动失败恢复及共享数据保留。`go test -short ./...` 跳过真实进程测试。Windows 和 macOS 的完整进程测试需要分别在对应系统运行；交叉编译只能验证平台代码可编译。
