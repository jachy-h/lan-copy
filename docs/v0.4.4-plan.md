# Lan Copy v0.4.4 计划

## 目标

实现 PDF 在线预览、DOCX 浏览器端预览和 XLSX/XLS 表格预览。旧版 `.doc` 不提供预览；不增加服务进程，继续使用单二进制与嵌入式前端。

调研及方案调整记录：2026-10-26。初期集成过纯 Go DOCX 转 PDF，随后根据需求改为浏览器端 HTML 预览，并撤销 Go 转换依赖。`.doc` 不预览，保留下载。

## 首期实现状态

- `.docx` 通过同源 `/preview-files/{name}` 读取原始 OpenXML 文件，在浏览器使用自托管 `docx-preview` 解析成 HTML；不经过服务端转换。服务端继续提供安全路径校验、固定 DOCX MIME、inline、Range/HEAD；`/files/{name}.docx` 继续作为原文件下载。
- `.doc` 不纳入预览白名单，文件仍显示在列表中并可下载。
- `docx-preview` 0.4.1（Apache-2.0）及 JSZip 3.10.2（MIT OR GPL-3.0-or-later）静态资源按需加载并嵌入 Go 二进制，预览输入上限 32 MiB；关闭 altChunk HTML、评论和修订渲染。字体取自浏览器/客户端环境，复杂布局和分页可能与 Word 不同。
- `.xls` / `.xlsx` 使用 SheetJS 0.20.3，在浏览器 Worker 中解析并显示文本表格；输入上限 32 MiB，每张工作表最多显示 250 行、50 列，最多显示 20 个工作表。公式显示缓存值，不执行宏；不提供完整 Excel 样式、图表或公式计算能力。
- 保留现有 PDF.js 6.4.299 预览路径。`allfile-preview` 的全量包虽然能统一 PDF/DOCX/Excel，但本版不直接替换：其包体内含 PDF.js 3.11.174 与 `xlsx@0.18.5`，Excel 依赖版本有公开安全公告；并且 UMD 整体约 2.16 MB，其中不少格式能力与现有预览重复。

## 调研结论

**技术上可接入，适合作为可选的浏览器端预览引擎进行 POC；不建议未经体积、许可和格式实测就直接用 Full 包替换现有预览器。**

File Viewer 提供原生 Web Component 和命令式 `mountViewer` API，支持无前端框架接入；主解析渲染在浏览器运行，Worker、WASM、字体和 vendor 资源可自托管。它可补齐 DOCX、XLSX、PPTX、OFD、CAD、压缩包等当前未覆盖的类型。其自身源码为 Apache-2.0，但 Full 渲染器中的 DWG/DWF/DWFx 运行时为 AGPL-3.0-only，若交付这些 CAD 能力需另行评估合规方式。

### allfile-preview 评估（2026-10-26）

- `@allfile-preview/core` 为 MIT 许可 Web Component，浏览器本地支持 PDF、DOCX、Excel 等；明确不支持旧版 `.doc`。当前 UMD 产物约 2.16 MB；压缩 npm 包约 0.94 MB，包含 PDF.js、docx-preview、SheetJS、marked 和 Lit。[仓库与格式矩阵](https://github.com/ankeji/allfile-preview) [npm 包](https://www.npmjs.com/package/@allfile-preview/core)
- 发布包依赖 `xlsx@^0.18.5`，npm 实际解析仍为 0.18.5。该版本早于 SheetJS 官方修复的 CVE-2023-30533 / CVE-2024-22363 范围；官方修复版本为 0.20.2 及以上，发布包并未使用修复版本。[CVE-2024-22363 官方公告](https://cdn.sheetjs.com/advisories/CVE-2024-22363) [修复说明](https://git.sheetjs.com/sheetjs/sheetjs/issues/3012)
- 包内 PDF.js 为 3.11.174，显著落后于当前项目已内嵌的 6.4.299；虽然旧版可通过 `isEvalSupported: false` 缓解一项已知问题，但替换会降低当前 PDF 引擎版本，且不值得为增加表格预览而重复部署整套能力。[Mozilla PDF.js 安全公告](https://github.com/mozilla/pdf.js/security/advisories/GHSA-wgrm-67xf-hhpq)
- 取舍：不采用 allfile-preview 全量 UMD 替换当前 PDF.js。DOCX 直接集成更小的 docx-preview；Excel 单独使用官方 SheetJS 0.20.3 浏览器构建，只启用 `.xls` / `.xlsx` 阅读，不把宏、公式重算、图表等能力视为支持承诺。

建议的候选路线：

1. 使用 Vanilla JS Web Component 或 `mountViewer`，不引入 Vue/React。
2. 使用 `@file-viewer/web-full` 做第一轮格式覆盖验证；如果运行时资源过大，再改为 `@file-viewer/web` + 选定 preset/renderer 的最小组合。
3. 将 JS、renderer chunks、Worker、WASM、字体和 vendor 资源固定版本后放入 `web/`，随 Go 二进制一起嵌入并通过同源静态路由提供；生产环境不依赖公共 CDN 或独立 Docker/转换服务。
4. 保留现有 `/preview-files/` 作为唯一文件读取入口，组件使用同源 URL，继续由 Lan Copy 校验共享目录路径、文件类型及 Range/HEAD 请求。预览能力仍为只读，不把任意本机路径或外部 URL 交给 viewer。
5. 先以新增支持格式为目标，暂不替换现有图片、音视频、文本和 PDF.js 路径；确认输出、内存和包体积后再决定是否合并 PDF 渲染器。

## 与当前实现的匹配点

- Lan Copy 的预览页是原生 HTML/JS，资源通过根目录 `assets.go` 的 `//go:embed web/*` 嵌入；不需要引入前端框架。
- `GET /preview-files/{name}` 提供带类型白名单、固定 MIME、inline、Range/HEAD 语义的同源预览资源。viewer 能直接读取可达 URL，也支持传入 `Blob`；应优先使用受控的同源 `/preview-files/` URL。
- 现有独立入口 `/preview.html?path=...` 与计划中的页内 `<dialog>` 均可挂载 Web Component，按文件打开后销毁组件 controller，复用既有生命周期。
- 后端当前为预览类型白名单；增加格式需同步扩展类型判断及文件响应头，而不是让前端组件绕过后端策略。Office 文档解析产生的 HTML/SVG/媒体需确认组件默认安全策略不执行不可信文件内容。
- CSP 当前对预览页限制为同源脚本、Worker、字体、图像和 WASM 执行能力；集成前必须查清各 renderer 实际需要的 `worker-src`、`connect-src`、`font-src`、`img-src`、`style-src` 与 WASM/CSP 要求，按最小权限逐项调整并保留 `frame-ancestors 'none'`。

## 主要收益与代价

### 收益

- 大幅扩展浏览器可预览格式，尤其 Office 文档及常见工程、归档格式。
- 前端解析避免部署 Office 转码服务、任务队列和临时转换文件。
- Worker/WASM 资源支持自托管，可用于无公网的局域网环境。
- 组件有统一挂载、更新、销毁 API，能适配当前页内弹窗和旧预览 URL。

### 代价与风险

- Full 包不只是一个 JS 文件：完整运行还需同版本 renderer chunks、Worker、WASM、字体和 vendor 资源；这些文件会进入仓库工作树及最终单二进制，下载、构建和发布体积可能显著增长。
- 多格式解析会消耗浏览器内存和 CPU；超大、损坏、加密或复杂格式文件需限制并实测。组件文档也明确格式注册不保证所有文件保真一致。
- 资源需与 npm 包版本严格匹配；漏嵌入或 MIME/CSP 路径错误会造成部分格式静默不可用，需构建检查资源清单及发布包。
- 引入第三方解析器扩大供应链和安全维护面；需锁定依赖、审阅许可证及安全公告，保留组件销毁与请求取消。
- Full 包内 DWG/DWF/DWFx 的 AGPL-3.0-only 运行时对分发 Lan Copy 二进制有额外合规影响。若不接受该要求，应选不含对应运行时的标准包/preset，并确认依赖树中不包含该运行时。
- Apache-2.0 主许可证不代表全部依赖和格式 renderer 都是 Apache-2.0；需要为实际发布的文件建立依赖与许可证清单。

## POC 范围与验证步骤

1. **锁定发行版本及许可证。** 记录 npm 包版本、仓库 tag、主许可证、完整依赖树及各 renderer 的许可证；重点确认 Full 是否拉入 AGPL CAD 包、是否能明确排除该能力。
2. **建立本地前端资源构建流程。** 不使用 CDN；从 npm 安装固定版本，将运行时 `dist` 资源放入 `web/` 中独立目录。确认 `assets.go` 嵌入规则能包含嵌套资源，检查路径大小写与静态 MIME（尤其 `.mjs`、`.wasm`、字体和 Worker）。不在运行时下载或解包依赖。
3. **接入临时预览入口。** 在原生 JS 页面挂载 viewer，传入 `/preview-files/{path}` 及文件名；保持文件只从 Lan Copy 文件服务读取。打开新文件前销毁旧 controller，关闭弹窗或离开页面时销毁解析器、媒体和监听器。
4. **核对安全响应。** 使用当前 CSP 和预览文件处理器运行各类格式，按浏览器控制台证据收紧或补充 CSP；验证脚本、外部网络请求、HTML/SVG、压缩包内部文档与恶意样本不会执行活动内容或访问未授权资源。检查 Worker/WASM MIME、Range 和错误响应。
5. **用代表文件核对功能与浏览器。** 至少验证 DOCX、XLSX、PPTX、PDF、OFD、ZIP、图片、文本与现有音视频；覆盖大文件、加密/损坏文件、取消加载、连续切换、销毁及窄屏。逐项记录 stable/experimental 状态，不将实验格式写成承诺支持。
6. **测量交付成本。** 记录前端新增资源体积、Go 二进制增量、冷启动/首次渲染时间和峰值内存；确认 `go build .` 后资源可用，构建无需联网，用户可在无公网环境运行。
7. **完成许可证与文档审查后再决定纳入。** 若 Full 体积或许可不适合，转为挑选 preset/renderer；若某格式质量不达标，保留现有路径或继续下载原文件。

## 兼容与安全边界

- 不新增服务进程、后端转换服务、外网依赖或运行时 npm 安装；保持单进程、单二进制、嵌入式前端。
- 不开放 `/preview-files/` 以外的文件读取方式，不接受任意 URL，不改变路径校验、共享目录边界、访问策略和恢复语义。
- 不因 viewer 需要而放宽跨源请求、CSP 或 `frame-ancestors 'none'`；确有资源策略需求时，按实际 renderer 最小增量调整并验证。
- 新格式需由后端明确允许并返回安全的 Content-Type；预览页展示错误和下载入口，不因解析失败影响列表及其他预览。
- 保持 `/preview.html` 深链接兼容；未来若统一页内弹窗，弹窗与旧预览页共用挂载/销毁代码。
- 重构或替换 PDF.js 前先单独比较 PDF 质量、分页/缩放交互、按需读取、体积及可访问性，不将其视为 File Viewer 接入的前置条件。

## 主要涉及位置（若 POC 通过）

- `web/preview.js`：按类型选择现有 renderer 或 File Viewer，封装组件挂载与销毁生命周期。
- `web/preview.html` 及页内弹窗：提供 viewer 容器和加载、错误、下载状态。
- `internal/httpserver/preview.go`、`internal/httpserver/file_handlers.go`：在批准的范围内扩展预览类型和响应 MIME。
- `internal/httpserver/routes.go`：确认嵌入式静态资源路由能正确提供新增嵌套文件和 MIME。
- `web/vendor/file-viewer/`（候选目录）：固定版本的运行时资产及许可证/来源说明；按实际文件布局决定，不能只复制入口 JS。
- `docs/DEVELOPING.md`、发布说明：记录资源更新流程、格式等级、许可证和体积边界。

## 决策门槛

只有以下条件全部满足，才建议在 0.4.4 正式集成：

- 能以自托管静态资源形式嵌入 Go 单二进制，并在离线局域网正常工作。
- 实测目标格式质量符合需求，失败可诊断，关闭和切换可完整销毁 renderer。
- 构建体积、运行内存与首次加载体验在项目可接受范围内，并有可复现测量数据。
- CSP、安全边界和第三方许可证均得到明确处理；若包含 AGPL renderer，项目明确接受其分发义务。
- 保留既有 API、路径校验、文件响应策略和 `/preview.html` 兼容入口。

## PDF 在线渲染方案

这里的“在线预览”指在浏览器中查看 Lan Copy 共享空间里的 PDF，包含用户事先转换后上传的 PDF；局域网访问即可工作，不要求公网。任意公网 PDF URL 的导入不是本版默认需求。现有代码已经提供这条预览链路。

### 当前能力与待补项

- `web/vendor/pdfjs/README.md` 记录当前内嵌 `pdfjs-dist 6.4.299`，包括 legacy library、Worker、CMaps、标准字体与 WASM，使用 Apache-2.0 及随包资源的许可证。
- `web/preview.js` 已通过 PDF.js display API 把单页绘制到 Canvas，支持上一页/下一页、指定页码、适合宽度与缩放，并限制画布像素量。当前加密 PDF 提示下载，没有密码输入流程。
- `/preview-files/{name}` 已支持 HEAD/Range，客户端设置 `disableAutoFetch: true`、`disableStream: true` 避免主动预取整个文档；实际读取量取决于 PDF 结构和 PDF.js 请求，不能承诺所有文件只读取当前页字节。
- 当前只渲染 Canvas，没有 PDF 文本层和注释层，因此文字选择、全文搜索、目录、可访问阅读及链接行为还需补充。签名有效性验证也不属于画布预览能力。
- 独立 `/preview.html` 配置了 Worker/WASM 所需 CSP；页内弹窗使用宿主页的 CSP，需同步核对首页与文本快传页，不能认为预览页的策略会自动应用于弹窗。

### 渲染方案比较

| 方案 | 部署与能力 | 对 Lan Copy 的判断 |
| --- | --- | --- |
| 现有 PDF.js display API + 自有 UI | JS/Worker/WASM 可嵌入前端；已有分页缩放，可逐步加入文本、注释、搜索和目录 | **首选。** 增量最小，继续复用同源文件接口和现有界面 |
| PDF.js 完整 viewer | 官方 viewer 构建于 display API，已有较完整阅读 UI；需要额外 viewer、样式、语言资源和宿主集成 | 作为功能参考或后续候选；若采用，应按官方要求定制界面，并处理与 dialog 的生命周期和工具栏重复问题。[官方分层说明](https://mozilla.github.io/pdf.js/getting_started/) |
| 浏览器原生 PDF viewer（新标签、`iframe` / `object`） | 浏览器负责阅读 UI，行为随浏览器和设备变化；应用较难统一控制加载、错误与销毁 | 可评估新标签作为辅助入口。当前资源带 `X-Frame-Options: DENY` 和 `frame-ancestors 'none'`，直接嵌入会被阻止；本版继续直接挂载 PDF.js |
| File Viewer 的 PDF renderer | 统一多格式预览入口，同时引入其组件、renderer 和运行时资产 | 只在 File Viewer 的整体 POC 中比较；未证实收益前保留现有 PDF.js，避免重复交付 PDF 引擎。[原生 JS 集成](https://doc.file-viewer.app/zh/guide/quickstart-web) |
| PDFium / MuPDF 服务端逐页转图片 | 需要 PDF 原生引擎、平台构建或外部工具，另需图片缓存；图片本身不保留文字选择和搜索能力 | 不作为常规 PDF 阅读方案。PDFium 使用 Chromium 的构建工具链；MuPDF 为 AGPL/商业双许可，维护成本需单独评估。[PDFium 构建](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/README.md)、[MuPDF 许可](https://mupdf.readthedocs.io/en/latest/license.html) |

PDF.js 的跨源 URL 读取受浏览器同源/CORS 策略约束。若未来增加公网 PDF URL，应单独设计来源限制与网络访问策略；不为当前共享文件预览新增任意 URL 代理。[PDF.js FAQ](https://github.com/mozilla/pdf.js/wiki/Frequently-Asked-Questions)

### 推荐实施顺序

1. 保持现有 PDF.js 和 `/preview-files/`，完善页内弹窗与独立预览页共用的挂载/销毁；取消旧 render task，销毁 loading task，清理缩放定时器，避免快速切换后旧内容覆盖新文件。
2. 优先补文字选择与文本层，再按实际需求增加搜索、目录及密码输入；注释、外链与附件动作需明确允许范围，不启用文档脚本或自动外部资源加载。
3. 保留单页或可视范围渲染与像素预算，搜索按需提取并可取消，避免全页 Canvas 常驻或一次性把所有页放入 DOM。
4. 使用中文字体、扫描件、横向页、大页幅、数百页、加密和损坏 PDF 验证显示与错误路径，并比较 localhost、LAN、移动端和主流浏览器。

## Word 预览与转换方案调研

本节记录前期对 Word 转 PDF 的调研。转换负责把 DOC/DOCX 排版为 PDF；PDF.js 负责读取 PDF。前端直接预览 Word 是 HTML 阅读模式，不会生成可复用 PDF。

| 方案 | 实际依赖与边界 | 建议 |
| --- | --- | --- |
| LibreOffice headless | 以 `soffice --headless --convert-to pdf:writer_pdf_Export --outdir ...` 转换 Word；需 LibreOffice 安装、字体、可写用户 profile 和子进程。可通过 `-env:UserInstallation=file:///...` 指定独立 profile | **服务端转换的首选验证候选**；需要先解决与单进程约束的冲突。[官方命令参数](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)、[PDF 导出参数](https://help.libreoffice.org/latest/en-US/text/shared/guide/pdf_params.html) |
| Gotenberg | 用 Docker/API 封装 LibreOffice 转换，适合已有转换基础设施；仍需额外容器、转换进程和服务运维 | 可作为未来用户自建的外部服务候选，不属于当前零依赖默认部署。[官方介绍](https://gotenberg.dev/docs/getting-started/introduction)、[转换 API](https://gotenberg.dev/docs/convert-with-libreoffice/convert-to-pdf) |
| Word 自动化 / COM | 依赖安装和授权的 Microsoft Office，平台及交互会话限制明显；微软提示无人值守环境存在挂起和稳定性问题 | 不作为跨平台后台转换方案。[微软说明](https://learn.microsoft.com/en-us/office/client-developer/integration/considerations-unattended-automation-office-microsoft-365-for-unattended-rpa) |
| Pandoc + PDF engine | 文档经过 Pandoc 的结构转换，再交给 LaTeX、Typst、HTML 等 PDF engine；增加可执行文件/字体依赖 | 适合内容转换；判断上不适合以保持原 Word 复杂版式为目标的默认预览。[Pandoc PDF engine](https://pandoc.org/MANUAL.html#option--pdf-engine) |
| DOCX → HTML → Chromium 打印 | 先自行解析 Word，再用浏览器打印 HTML；Chromium 的 PDF 接口处理网页，不能直接替代 Word 排版引擎 | 需要额外浏览器进程，且需验证两次转换后的分页、页眉页脚和浮动对象；不作为本版首选。[Playwright page.pdf](https://playwright.dev/docs/api/class-page#page-pdf) |
| 用户先导出 PDF 后上传 | 使用用户自己的 Word/办公软件生成 PDF，Lan Copy 仅预览结果 | **当前架构下可直接采用**，无需新增服务端转换依赖 |

LibreOffice 的输出不保证与 Microsoft Word 完全一致；字体、复杂排版和嵌入对象需样本比对。Gotenberg 官方也明确提示复杂样式可能产生差异。LibreOffice 主许可为 MPL-2.0，同时包含其他许可证的组件；若分发安装包、字体或引擎资源，需检查实际发行物的许可。[转换限制](https://gotenberg.dev/docs/convert-with-libreoffice/convert-to-pdf)、[LibreOffice 许可证](https://www.libreoffice.org/licenses/)

### 与架构规则的冲突及当前决定

现有 `AGENTS.md` 要求“保持单进程、单二进制与嵌入式前端”。调用本机已安装的 LibreOffice，即使只启动短时子进程，也已经不满足严格的单进程要求；把转换器压进二进制后运行时释放执行，仍会增加进程、落盘资源和平台依赖。Gotenberg 则明确增加服务与容器。因此不能把这两条路线标为已符合项目架构。

**当前采用 PDF.js 预览 PDF、docx-preview 在浏览器渲染 DOCX，旧版 `.doc` 不预览；下载原文件保留。** 不承诺从 Word 生成 PDF。allfile-preview 全包不用于替换 PDF.js：包内 PDF.js 版本较旧，并包含有安全公告范围的 SheetJS 版本；如增加 Excel，需单独选用修复后的解析器并限定支持格式。

### 更轻量的候选与优先级

“轻量”先按无外部办公软件、无新增服务/子进程、可嵌入现有 Go 程序评估；资源体积、字体和内存仍需单独测量。以下候选主要针对 `.docx`，不能将其支持范围延伸到旧二进制 `.doc`。

| 候选 | 轻量之处 | 限制与决定 |
| --- | --- | --- |
| `bobyeoh/docx2pdf-go` | MIT 许可；纯 Go 库和 CLI，无 CGO、LibreOffice 或 Word 依赖；库调用在 Lan Copy 进程内运行 | **曾短暂集成，后按需求撤销。** 固定 v0.3.0，仅支持 DOCX 且有复杂版式降级；不再是当前运行依赖。[项目与格式边界](https://github.com/bobyeoh/docx2pdf-go) |
| UniOffice + UniPDF | 官方提供 Go 进程内布局与 PDF 输出，不需安装 Word；转换需要两个产品的许可配置 | 商业授权候选，需确认开源项目分发条款、离线授权、成本和转换质量；官方转换包仍有 beta 提示，不能仅因商业产品就假定高保真。[转换指南](https://docs.unidoc.io/unioffice/guides/document/converting-to-pdf/document-to-pdf/)、[许可加载](https://docs.unidoc.io/unioffice/getting-started/) |
| `docx-preview`（docxjs）+ 用户浏览器打印 | Apache-2.0；依赖 JSZip，在浏览器将 DOCX 渲染为 HTML，无新增服务端转换引擎 | 适合轻量在线预览及用户手动“打印/另存 PDF”；HTML 能力和分页有限，不能作为自动服务端 PDF 转换接口。[项目说明](https://github.com/VolodymyrBaydalka/docxjs) |

`docx2pdf-go` v0.3.0 的 `go.mod` 曾要求 **Go 1.26.1**，这正是它接入期间提升 Go 指令的原因。当前已移除该依赖，并将 `go.mod` 恢复到项目原有的 `go 1.22` 指令；本机使用 Go 1.27.3 构建不改变项目声明的最低 Go 版本。

该候选的验证步骤：

1. 固定源码 tag 和依赖，审查实现及测试依据。README 对部分复杂特性的支持描述存在前后不一致，功能清单仅用于挑选样本，不作为已通过验收的证据。
2. 核对字体格式与许可，选择可分发的中文 TrueType 字体；测量带字体后的实际发布体积、内存和首次转换时间，不以仅带拉丁字体的 CLI 大小做结论。
3. 比较中文合同、表格跨页、页眉页脚、图片、公式、目录、文本框和修订文档；重点发现静默漏内容、对象占位、分页差异和字体缺字。先定义基础 DOCX 支持范围，再决定是否能用于预览。
4. 审查 ZIP 解压大小、图片像素和 XML 解析限制，验证并发调用及取消检查。进程内转换不能通过结束子进程强制回收资源，`context` 超时也不保证能立即中断任意布局阶段；这是正式启用前的决策条件。
5. 后续在 Windows/macOS/Linux 验证工具链、字体路径及构建可行性；衡量包含 Go 1.26.1 工具链要求后的发布影响。发现体积、质量或资源边界不符合预期时，保留下载原文件和用户上传 PDF 的路径。

### 若后续允许外部转换器，必须具备的设计

1. **组件职责。** 转换组件持有任务、队列和缓存状态，HTTP 层只做路径/访问校验、参数和状态码处理，应用层负责组装；真实实现时再创建内聚组件，不预建空包。源文件读取继续调用文件存储边界。
2. **转换环境。** 由服务主机显式配置并探测 LibreOffice 可执行文件与版本，使用参数数组调用，避免 shell 拼接。每个受控 worker 使用独立 profile；先限制单任务转换，再依据实测决定是否增加 worker。平台实现与进程树回收分别处理 Windows、macOS、Linux。
3. **源文件一致性。** 通过文件存储组件安全打开普通文件，复制为私有任务快照并计算摘要；限制快照大小，检测复制期间的变化。转换器只读取快照，不凭用户路径再次打开源文件。源文件版本已变化时，不将旧结果绑定到新版本。
4. **缓存正确性。** 缓存键包含源内容摘要、转换器版本、导出参数与字体配置版本；仅使用路径或 mtime 不足以标识内容。并发相同任务合并，结果检查 PDF 可读性及大小后原子提交；缓存读取重新确认源文件可访问及版本一致。
5. **资源限制。** 限制源大小、排队数、运行时间、输出大小及缓存总量；配置的超时须能结束对应进程树。HTTP 请求取消与共享任务取消分开处理，某一查看者关闭页面不影响仍被其他查看者使用的同一任务。跨平台硬内存/CPU 限制和沙箱属于需要验证的能力，不能仅凭 `--headless` 宣称已隔离。
6. **不可信输入。** 禁用宏、交互弹窗和外部链接更新，隔离用户配置与工作目录；确认引擎不能读取共享范围外文件或访问外部网络。LibreOffice CLI 参数本身不是安全沙箱；若无法提供所需隔离，不对 LAN 任意上传文件启用自动后台转换。
7. **持久化与清理。** 缓存、profile、输入快照和输出临时文件放入应用管理目录下独立子目录，不在共享文件列表展示；成功、失败、取消和启动恢复都清理残留，设置容量与过期淘汰，不占用或修改上传事务记录。
8. **协议与用户体验。** 源文件 `/preview-files/` 继续返回原文件，派生 PDF 使用受同一访问策略保护的独立入口；只对已完成结果支持 HEAD/Range 与 `application/pdf`。生成任务不得由 HEAD 触发，创建任务使用明确的请求方法与现有请求来源校验。页面展示等待、转换失败、缺依赖及下载原文件操作，避免长请求无反馈。
9. **字体与质量。** 建立可重复的字体环境，记录字体来源和许可；覆盖中文、英文、混排、表格跨页、页眉页脚、目录、公式、浮动图片、修订和加密文件。缺字体和版式变化须可识别，不承诺与 Word 完全一致。

### 验证和最终取舍

- PDF 渲染：验证按需读取、文本层、缩放、密码/损坏提示、加载中关闭、快速切换及资源释放；保持原文件下载和旧预览链接兼容。
- 转换验证：继续记录依赖安装成本、字体配置、首转/缓存命中耗时、峰值内存、输出体积和 Word 对照效果，不预填未经测量的性能结论。
- 任务与缓存：覆盖相同文件并发请求、源文件转换中被修改/删除、超时、进程崩溃、服务重启及缓存淘汰，确保不显示旧结果、不遗留转换进程、不泄露临时文件。
- 构建与发布：文档研究阶段无需构建；涉及实现后执行受影响测试与 `go build .`，检查 Windows/macOS/Linux 的资源、路径、进程生命周期和启动恢复。若采用可选转换器，还需验证未安装转换器时原有功能正常可用。
