# Lan Copy v0.8.0 Plugin Service Manager 计划

制定日期：2026-11-17。状态：**已批准，已实现并发布 v0.8.1**。

## 一、调研结论

### 1.1 现有架构

Lan Copy 当前是 Go 单二进制 + 内嵌 Vue SPA，无数据库、无 ORM、无通用任务队列、无用户账号体系：

| 关注点 | 现状 | 对本任务的影响 |
| --- | --- | --- |
| 入口 | `main.go`、`startup.go` 只传版本/公钥/内嵌资源 | 保持薄入口，不新增根目录命令 |
| 组装 | `internal/app` 的 `Prepare` / `Run` 组装组件与 HTTP | 在 `Prepare` 创建插件存储，在 `Run` 注入 Manager 并在 HTTP 启动后异步恢复 |
| HTTP | `internal/httpserver`，`net/http.ServeMux` 方法+路径路由 | 新路由继续用 `GET /api/...` 风格注册到 `routes.go` |
| 持久化 | 私有数据目录 `~/.lan-copy-app-data-<共享目录名>/`，JSON + 临时文件 + fsync + rename + 备份（`textstore`、`deploytoken`） | **复用该模式，不引入数据库**；插件状态同样放私有目录 |
| 文件上传 | `filestore` 事务目录、`http.MaxBytesReader`、multipart 流式读取、空闲超时、`-max-gb` | 镜像上传复用流式写入和大小限制，但不解压到共享目录 |
| 权限 | 无账号；`isLocalRequest` 区分本机/局域网；写操作要求 `X-Lan-Copy-Action` + 同源校验 | “管理员”映射为**本机用户**；插件管理全部仅本机 |
| 后台任务 | 无 TaskManager；打印任务用内存状态+`go submit`，上传进度只在前端 | 新增最小任务注册表（内存 + 有界持久化），不引入队列框架 |
| 前端 | Vue 3 + TS，Vite 多 HTML 入口；`App.vue` 按路径切换页面；`frontend/` 是源码，`web/` 是生成产物 | 新增 `/plugins` 页面需同步 `vite.config.ts`、`sync-assets.mjs`、`routes.go`、`web/` 产物 |
| 组件测试 | 组件测试与实现相邻；HTTP 测试用 `httptest`；前端 vitest + Playwright | 新包采用同一方式；Docker Runtime 通过接口 Mock，另加可选真实 Docker 集成测试 |
| 构建 | `go.mod` 目前**零依赖**，`CGO_ENABLED=0` 交叉编译 Windows amd64 / macOS arm64；CI 在 Linux/Windows/macOS 跑 `go vet`/`go test` | 引入 Docker SDK 会新增 `go.sum` 与传递依赖，需明确批准 |

### 1.2 与既有 v0.7.0 计划的关系

`docs/v0.7.0-plan.md` 已规划“发票 OCR + 本地服务管理”，其中服务管理采用 **docker CLI**，与本任务“禁止业务代码执行 docker CLI、优先 Docker 官方 SDK”的要求冲突。该计划尚未实现、尚未批准。

本计划只覆盖 **通用 Plugin Service Manager**：

- 不修改 v0.7.0 文档；其“本地服务管理”一节由本计划取代。
- 发票 OCR 以后可以作为本管理器的一个插件接入，不在本版范围。

### 1.3 关键现状约束

1. **零依赖**：`go.mod` 只有 `module` 与 `go 1.22`，没有 `go.sum`。引入 Docker 官方 SDK 会改变“仅标准库”的构建属性。
2. **无数据库**：需求中的表将实现为私有数据目录中的版本化 JSON 集合，并通过单个原子快照保证跨实体一致性。
3. **无管理员账号**：只能以“本机请求 + 动作头 + 同源”作为管理员边界；不新建登录系统。
4. **部署形态**：现有发布形态是宿主机双击/命令行运行，Go 不在容器内。因此默认网络模式必须是**回环端口**，不能假设宿主能解析容器 DNS。
5. **Docker 可用性**：本机已安装 Docker 29.8.2，可用于集成验证；Docker 不可用时必须明确降级，不能影响现有文件、碎片、打印、更新功能。

## 二、总体设计

```text
Vue /plugins 页面
      │  本机 + 动作头 + 同源
      ▼
internal/httpserver
      │
      ▼
internal/plugin（领域、Manager、Registry、Manifest、Client、任务）
      │                  │
      │                  └──► <dataDir>/plugins/*.json（私有状态）
      ▼
internal/plugin.Runtime（接口，不依赖 Docker）
      │
      ▼
internal/plugin/dockerruntime（唯一导入 Docker SDK 的包）
      │
      ▼
Docker Engine API（unix socket / Windows named pipe / DOCKER_HOST）
```

依赖方向：`httpserver → plugin ← dockerruntime`，`app` 负责把二者组装起来。`plugin` 不导入 Docker SDK，`dockerruntime` 不导入 HTTP 层。

### 2.1 新增包

```text
internal/plugin/
  types.go            领域模型、状态、配置、健康记录、任务
  manifest.go         Manifest 结构、严格校验、协议兼容
  store.go            版本化 JSON 状态、原子写入、备份、恢复
  runtime.go          Runtime 接口与运行时无关的请求/响应类型
  manager.go          注册、安装、生命周期、状态同步、健康检查
  tasks.go            有界异步任务
  client.go           统一 HTTP Client、错误分类、限额、指标
  secrets.go          AES-256-GCM 环境变量加密
  paths.go            数据目录白名单与挂载路径校验
  *_test.go

internal/plugin/dockerruntime/
  runtime.go          SDK 连接、Ping/Info、镜像导入/检查/删除、网络
  container.go        容器创建/启停/检查/日志/统计
  convert.go          安全 HostConfig/NetworkingConfig 构造（纯函数）
  convert_test.go     安全不变量测试
  runtime_test.go     假 Engine 接口测试
  integration_test.go 真实 Docker 测试（环境变量跳过）
```

不新增 `pkg/`、不拆分 module、不引入 ORM、不引入 CLI 执行层。

### 2.2 运行时接口

```go
type Runtime interface {
    Info(ctx context.Context) (RuntimeInfo, error)

    PullImage(ctx context.Context, req PullImageRequest) (ImageInfo, error)
    ImportImage(ctx context.Context, r io.Reader, req ImportImageRequest) ([]ImageInfo, error)
    InspectImage(ctx context.Context, reference string) (*ImageInfo, error)
    RemoveImage(ctx context.Context, reference string, force bool) error

    EnsureNetwork(ctx context.Context, name string) error

    Create(ctx context.Context, req CreateInstanceRequest) (*InstanceInfo, error)
    Start(ctx context.Context, runtimeID string) error
    Stop(ctx context.Context, runtimeID string, timeout time.Duration) error
    Restart(ctx context.Context, runtimeID string, timeout time.Duration) error
    Remove(ctx context.Context, runtimeID string) error

    Inspect(ctx context.Context, runtimeID string) (*InstanceInfo, error)
    List(ctx context.Context, labels map[string]string) ([]InstanceInfo, error)
    Logs(ctx context.Context, runtimeID string, opts LogOptions) (io.ReadCloser, error)
    Stats(ctx context.Context, runtimeID string) (*Stats, error)
}
```

要点：

- `ImageInfo` 包含引用、digest、架构/系统、大小、标签、`Config.User`、镜像 ID。
- `CreateInstanceRequest` 只接受已校验的高层参数（镜像、环境变量、端口、挂载、CPU/内存/PID）；**没有** `privileged`、`networkMode`、`extraHosts`、`devices`、`capAdd`、`hostConfig` 等透传字段。
- `LogOptions` 只有 `Tail`、`Timestamps`、`Since` 和最大字节数。
- Docker SDK 的错误在 `dockerruntime` 内转换为 `ErrRuntimeUnavailable`、`ErrNotFound`、`ErrConflict` 等领域错误。

### 2.3 Docker SDK 选择

推荐使用 Docker 官方拆分后的 Engine SDK：`github.com/moby/moby/client` + `github.com/moby/moby/api`（`github.com/docker/docker/client` 的正式后继）。已在本机临时模块验证：

- 可下载、可编译。
- `CGO_ENABLED=0` 交叉编译 Windows amd64 与 macOS arm64 通过。
- 需要把 `go.mod` 的 `go` 指令提升到 **1.24**（SDK 要求）；`go.sum` 约 41 条直接/间接依赖。
- 通过 `client.FromEnv` 支持 `DOCKER_HOST`、unix socket、Windows named pipe；不执行任何 docker 命令。

放弃 `github.com/docker/docker v27.x+incompatible`：该模块没有有效 go.mod，传递依赖无法稳定锁定（实测与当前 `go-connections` 组合编译失败）。

> 备选：用标准库直接实现 Docker Engine HTTP 客户端（unix socket + 自写 Windows named pipe）。可保持零依赖，但 Windows npipe 与日志多路复用需要自行实现，风险与代码量明显更高；不建议首期采用。此项需在批准时确认。

## 三、数据模型与持久化

### 3.1 领域模型

JSON 字段沿用项目现有 API 的 lowerCamelCase 风格。

```go
type Plugin struct {
    ID              string    // manifest.id，全局唯一，主键
    Name            string
    Description     string
    Category        string
    ProtocolVersion string
    CurrentVersion  string
    Status          Status
    CreatedAt       time.Time
    UpdatedAt       time.Time
}

type Image struct {
    ID           string    // 随机 ID
    PluginID     string
    Reference    string    // name:tag
    ImageName    string
    ImageTag     string
    Digest       string
    Registry     string
    Architecture string
    OS           string
    SizeBytes    int64
    Source       string    // upload（首期唯一来源）
    Manifest     Manifest  // 导入时从镜像标签读取并校验的快照
    CreatedAt    time.Time
}

type Instance struct {
    ID                string
    PluginID          string
    ImageID           string
    RuntimeType       string // docker
    RuntimeInstanceID string // 容器 ID
    ContainerName     string
    InternalAddress   string
    HostPort          int
    Status            Status
    HealthStatus      HealthStatus
    StatusReason      string
    RestartCount      int
    StartedAt         *time.Time
    LastHealthAt      *time.Time
    Config            Config
    CreatedAt         time.Time
    UpdatedAt         time.Time
}
```

`Config`：

```go
type Config struct {
    Env                  []EnvVar      // Name / Value / Secret
    CPULimit             float64       // 0.1–8.0
    MemoryMB             int64         // 64–16384
    PIDsLimit            int64         // 16–4096
    RestartPolicy        string        // no | on-failure[:N]
    Mounts               []Mount       // HostPath / ContainerPath / ReadOnly
    HealthCheck          HealthConfig  // Path / IntervalSeconds / TimeoutSeconds / Retries / StartupTimeoutSeconds
    RequestTimeoutSeconds int          // 1–300
    LogMaxSizeMB         int           // 1–50
    LogMaxFiles          int           // 1–5
}
```

`HealthStatus`：`unknown | checking | healthy | unhealthy`。
`Status`：`not_installed | installing | stopped | starting | running | unhealthy | stopping | failed | uninstalling`。

结构上 `Instances` 是切片，管理器 v1 只允许每个 Plugin 一个实例；未来多实例不需要改存储格式。

### 3.2 状态文件

```text
<dataDir>/plugins/
  state.json          # 0600，原子写入
  state.backup        # 0600，上一次成功快照
  secret.key          # 0600，32 字节随机密钥（仅首次创建）
  tmp/                # 0700，镜像上传临时文件，任务结束清理
  data/               # 0700，默认允许的持久化根目录
```

`state.json` 版本 1：

```json
{
  "version": 1,
  "plugins": [], "images": [], "instances": [],
  "tasks": [], "healthRecords": { "<instanceId>": [] }
}
```

与需求中五张表的对应关系：

| 需求表 | 本实现 |
| --- | --- |
| `plugin_services` | `state.plugins` |
| `plugin_images` | `state.images` |
| `plugin_instances` | `state.instances` |
| `plugin_tasks` | `state.tasks` |
| `plugin_health_records` | `state.healthRecords` |

选择单个快照而不是五个文件：安装/启动会同时修改插件、实例、任务和健康记录，单文件可在一次 rename 中保证一致，避免跨文件半写。写盘流程复用 `textstore` 的模式：同目录临时文件 → `Chmod(0600)` → `Sync` → `Rename` → 目录 `Sync`；成功写盘后把旧快照复制为 `state.backup`。启动时主文件损坏/缺失则尝试备份，仍失败则报错并保留两份内容，不静默覆盖。

有界策略：

- 任务最多保留 100 条；运行中任务在启动恢复时标记为 `failed`，原因“服务重启，任务中断”。
- 每个实例最多保留 50 条健康记录（环形）。
- 单个任务消息/错误各限制 4 KiB；健康错误限制 2 KiB。
- 不持久化插件日志正文、请求体、环境变量明文。

### 3.3 敏感环境变量

- 值使用 AES-256-GCM 加密，存储格式 `enc:v1:<base64(nonce||ciphertext)>`。
- 密钥优先取环境变量 `LAN_COPY_PLUGIN_SECRET_KEY`（base64 32 字节）；未配置时使用 `secret.key`（0600，首次启动生成）。
- API 读配置时 secret 值始终返回空字符串并标记 `secret: true`；更新时省略值表示保留原值。
- 日志、任务错误、HTTP 错误、调试输出都不包含明文。
- 密钥丢失时，相关实例拒绝启动并给出明确错误，不以空值继续运行。
- 诚实说明：同用户权限的本地进程仍可读取密钥和状态文件；该加密用于避免明文落盘与备份泄露，不等同于操作系统密钥链。

## 四、插件协议与 Manifest

### 4.1 HTTP 协议

插件必须实现：

| 方法 | 路径 | 要求 |
| --- | --- | --- |
| GET | `/health` | 200 + `{"status":"ok","version":"..."}` |
| GET | `/manifest` | 与导入时 Manifest 一致 |
| GET | `/version` | 插件版本、构建版本、运行时信息 |
| GET | `/capabilities` | 能力与接口描述 |

业务接口由插件自行定义；Lan Copy 不为每个插件编写 Docker 代码。

### 4.2 安装时 Manifest 来源

首期要求镜像通过 OCI label 携带 Manifest：

```dockerfile
LABEL io.lan-copy.plugin.manifest='{"schemaVersion":1,...}'
```

理由：不需要启动不可信镜像即可读取；不依赖额外上传可篡改的 JSON；`docker save` 上传后仍然存在。

安装/启动后的身份校验仍通过 HTTP：

1. 启动后 `GET /manifest`，严格校验。
2. `id` 必须等于镜像 label 中的 ID 和安装时声明的 ID。
3. `protocolVersion` 主版本必须兼容。
4. 服务端 `version` 与镜像 Manifest 版本不一致时记录警告；`id` 不一致直接失败。

不使用“启动临时容器读取 Manifest”方案：它会执行不可信镜像代码，且需要端口/网络隔离，收益低于 label。

### 4.3 Manifest 结构

```json
{
  "schemaVersion": 1,
  "id": "invoice-ocr",
  "name": "Invoice OCR",
  "version": "1.0.0",
  "description": "Chinese VAT invoice recognition",
  "protocolVersion": "1.0",
  "runtime": "http",
  "containerPort": 8080,
  "endpoints": {
    "health": "/health",
    "manifest": "/manifest",
    "version": "/version",
    "capabilities": "/capabilities"
  },
  "capabilities": ["invoice.recognize"],
  "defaults": {
    "cpuLimit": 0.5,
    "memoryMB": 512,
    "pidsLimit": 128,
    "requestTimeoutSeconds": 30,
    "startupTimeoutSeconds": 60
  }
}
```

校验规则（`DisallowUnknownFields` + 数量/长度上限）：

| 字段 | 规则 |
| --- | --- |
| `schemaVersion` | 必须为 1 |
| `id` | `^[a-z0-9][a-z0-9-]{0,63}$` |
| `name` | 1–100 字符，不允许控制字符 |
| `version` | `^[0-9A-Za-z][0-9A-Za-z.+-]{0,63}$` |
| `protocolVersion` | 必须为 `1.0`；仅接受主版本 1 |
| `runtime` | 必须为 `http` |
| `containerPort` | 1024–65535 |
| `endpoints.*` | 以 `/` 开头，长度 ≤ 256，不允许 `..`、查询串、片段、控制字符；四个端点必须存在 |
| `capabilities` | ≤ 64 项；每项 `^[a-z0-9]+(\.[a-z0-9-]+)+$`，≤ 128 字符；不重复 |
| `defaults` | CPU 0.1–8.0、内存 64–16384 MB、PID 16–4096、超时 1–300 秒、启动超时 10–300 秒 |
| 其他字段 | 一律拒绝（包括 `command`、`entrypoint`、`volumes`、`networkMode`、`privileged`、`ports`、`hostConfig`） |

镜像必须声明非 root `USER`（`User` 非空且不是 `root`/`0`/`0:0`），否则拒绝导入/安装。

## 五、安装与生命周期

### 5.1 镜像导入（首期唯一镜像来源）

```text
浏览器选择 .tar / .tar.gz
  → 仅本机 + 动作头校验
  → 大小限制（默认 2 GiB）+ 扩展名 + 魔数校验
  → 流式写入 <dataDir>/plugins/tmp/upload-<random>.tar[.gz]
  → 同时计算 SHA256
  → Docker ImageLoad
  → 收集 load 输出中的镜像引用；逐个 ImageInspect
  → 恰好一个镜像带合法 io.lan-copy.plugin.manifest
  → 校验架构/系统与非 root 用户
  → 创建/更新 Plugin（not_installed）与 Image 记录
  → 清理临时文件
  → 任务成功，返回 imageId
```

- **上传不自动安装、不自动启动。**
- 同一任务只允许一个导入在跑（信号量 1），避免磁盘与 Docker 峰值。
- 临时文件在成功、失败、取消、进程退出恢复时都清理。
- 上传文件名只用于扩展名判断，不参与路径。
- Registry 拉取按需求“暂时不做”；`Runtime.PullImage` 保留接口，Docker 实现返回 `ErrNotSupported`，不暴露 API/UI。

### 5.2 安装

```text
选择 imageId（可带 expectedPluginId）
  → 校验镜像记录、Manifest、协议版本、架构、非 root
  → 校验配置（资源、env、挂载、路径）
  → 若该 Plugin 已有实例：409
  → 创建 Plugin/Instance 记录，状态 installing
  → 构造固定安全参数并创建容器（不启动）
  → 持久化容器 ID、地址
  → start=true 时转 running 流程；否则 stopped
```

创建容器失败时回滚本次记录；镜像记录保留。

### 5.3 启动

```text
状态 starting
  → 检查镜像存在；容器不存在则按已存配置重建
  → Start
  → 轮询 /health（启动超时 10–300 秒，间隔 500ms–2s）
  → GET /manifest，校验 id / protocolVersion
  → 成功：running + health healthy + startedAt
  → 超时/失败：unhealthy 或 failed，保留容器与具体原因
```

健康检查失败不自动删除容器，用户可查看日志、重试或停止。

### 5.4 停止 / 重启 / 卸载

- 停止：`stopping` → 优雅 stop（默认 10 秒）→ 超时 force → `stopped`；容器不存在视为已停止。
- 重启：停止后启动，状态回到 `starting`。
- 卸载：`uninstalling` → 停止 → 删除容器 → 删除实例 → 删除插件记录 → 可选删除镜像 → 可选删除数据目录。
  - 默认保留镜像和持久化数据。
  - 删除数据必须由调用方显式传 `deleteData=true`，前端做二次输入确认。
  - 镜像仍被其他实例引用时拒绝删除（409）。

### 5.5 启动同步与异常恢复

HTTP 启动后异步执行，不阻塞服务：

1. Docker `Info`；不可用则标记管理器不可用，不报启动错误。
2. 确保 `plugin-network` 存在（bridge，带管理标签）。
3. 加载状态；中断任务标记失败。
4. 对每个实例 `Inspect`：
   - DB running + 容器 running → 保持 running，立即健康检查。
   - DB running + 容器 exited → `failed`（非 0 退出码）或 `stopped`，记录原因。
   - DB stopped + 容器 running → 以实际为准，改为 running 并健康检查。
   - DB 有记录 + 容器不存在 → `failed`，原因“容器不存在”；下次启动会重建。
   - 容器有管理标签但 DB 无记录 → 报告为 orphan，**不自动删除**。
5. 启动后台循环：每 15 秒健康检查，每 30 秒 Inspect 同步；状态变化写盘。
6. 进程正常退出：取消循环；默认优雅停止托管容器（可在设置中关闭）；写盘。崩溃残留下次接管。

### 5.6 并发

- 每个实例一把操作锁；同一实例的启动/停止/重启/卸载互斥，冲突返回 409。
- 全局状态锁只保护内存快照与写盘，不包裹 Docker 调用。
- 任务总量上限 8；镜像导入并发 1。

## 六、容器安全

`dockerruntime` 固定构造参数，业务层无法透传：

| 项 | 固定值 |
| --- | --- |
| 用户 | 镜像 `USER` 必须非 root；容器不额外提权 |
| 根文件系统 | `ReadonlyRootfs: true` |
| 临时目录 | tmpfs `/tmp`，默认 128 MiB，`noexec,nosuid,nodev` |
| 特权 | `Privileged: false` |
| Capabilities | `CapDrop: ["ALL"]`，不添加任何 capability |
| 提权 | `SecurityOpt: ["no-new-privileges"]` |
| PID/网络/IPC/UTS | 不使用 host 模式 |
| Docker Socket | 不允许挂载；挂载路径校验明确拒绝 |
| 设备 | 不添加 |
| 网络 | 只加入 `plugin-network`；容器内端口默认只发布到 `127.0.0.1` 随机端口 |
| CPU/内存 | `NanoCPUs`、`Memory`，`MemorySwap=Memory`（关闭额外 swap） |
| PID | `PidsLimit` |
| 日志 | json-file，`max-size` / `max-file` 受限 |
| 重启策略 | 默认 `no`；可选 `on-failure[:N]`；禁止 `always` / `unless-stopped` |
| 容器名 | `lan-copy-plugin-<pluginId>-<instanceShort>`，由管理器生成 |
| 标签 | `io.lan-copy.managed=true`、`io.lan-copy.plugin.id`、`io.lan-copy.instance.id`、`io.lan-copy.version` |

持久化目录：

- 默认允许根：`<dataDir>/plugins/data`；首期只在安装/配置时允许管理员明确选择该根目录下的子目录，后续可通过 Manager 选项增加更多本机根目录。
- 挂载的宿主路径必须绝对、`Clean`、解析软链接后仍位于允许根内；拒绝 `docker.sock`、`/var/run`、`/proc`、`/sys`、`/dev` 等敏感位置。
- 容器路径必须绝对、非 `/`、无 `..`，拒绝系统目录和 `/tmp`。
- 只允许 bind mount；不允许 volume driver、设备、传播模式。
- 默认不挂载共享目录，插件只能通过 HTTP 接收数据。

网络模式：

| 模式 | 适用 | 行为 |
| --- | --- | --- |
| `loopback`（默认） | Go 运行在宿主机（现有发布形态） | 发布 `127.0.0.1::<containerPort>`，Inspect 读取实际宿主端口，Client 使用 `127.0.0.1:<port>` |
| `container` | Go 也运行在 Docker 中 | 不发布端口，Client 使用 `http://<containerName>:<containerPort>`；要求 Lan Copy 容器已加入 `plugin-network` |

通过 `-plugin-network-mode=loopback|container` 和 `-plugin-network=plugin-network` 配置；不做自动猜测。容器部署文档会给出 `docker run --network plugin-network -v /var/run/docker.sock:...` 示例，并说明 socket 只暴露给 Lan Copy 主服务，绝不暴露给插件。

访问控制：

- 所有 `/api/plugins*` 接口（含 GET 状态/日志）仅本机可调用。
- 写操作要求 `X-Lan-Copy-Action: plugins`（上传为 `plugins-image`）+ 同源校验，复用 `validLocalActionRequest`。
- 局域网请求返回 403；不新增账号/会话系统。

## 七、Plugin HTTP Client

```go
type Client struct{ ... }

func (m *Manager) Call(ctx context.Context, pluginID string, req Request) (*Response, error)

type Request struct {
    Method   string
    Path     string        // 插件内路径，不允许绝对 URL / scheme / host
    Query    url.Values
    Header   http.Header
    JSON     any           // 与 Multipart/Body 互斥
    Multipart *MultipartRequest
    Body     io.Reader
    Timeout  time.Duration // 0 使用插件配置
    MaxBytes int64         // 0 使用默认
}

type MultipartRequest struct {
    Fields []Field
    Files  []FilePart      // 流式 io.Reader，不整体缓冲
}
```

能力：

- 根据 pluginID 找到唯一实例，校验状态并生成地址；业务层不拼接容器 IP/端口。
- 支持 GET/POST/PUT/DELETE、JSON、multipart/form-data、文件上传、文件下载。
- 默认超时 30 秒（插件可配 1–300 秒），响应头超时 10 秒；下载同样受 context 与总时限约束。
- 默认响应上限 8 MiB；下载默认 64 MiB；始终 `io.LimitReader`，超限返回明确错误。
- 默认禁止跨主机重定向（只允许同实例同源）。
- 不在默认失败时重试；首期不实现自动重试。
- 统一错误：`ErrPluginNotInstalled`、`ErrPluginNotRunning`、`ErrPluginUnhealthy`、`ErrPluginTimeout`、`ErrPluginUnavailable`、`ErrPluginProtocolMismatch`、`ErrPluginRequestFailed`、`ErrPluginResponseTooLarge`。
- 错误包装保留 `errors.Is`/`errors.As`，附插件 ID、状态码、脱敏摘要，不含请求体与环境变量。
- 每次调用更新内存指标：调用数、错误数、最近耗时、累计耗时、最近错误时间；在详情/状态接口返回。重启清零，不写盘。

| 情况 | 状态码 |
| --- | --- |
| 参数/Manifest/配置非法 | 400 |

## 十五、安全风险与缓解

| 风险 | 缓解 |
| --- | --- |
| Docker 管理等价高权限 | 所有接口仅本机 + 动作头 + 同源；不向局域网开放 |
| 恶意镜像 | 上传即运行本机代码；明确风险提示、显式安装确认、固定安全参数；不承诺镜像审计 |
| 容器逃逸/提权 | 非 root、read-only、cap-drop ALL、no-new-privileges、无 host 命名空间、无设备、无 socket |
| 任意宿主机挂载 | 挂载白名单根目录、路径解析与拒绝列表、默认不挂载共享目录 |
| 镜像包路径穿越 | 不在宿主解压任意路径；仅交给 Docker ImageLoad；临时随机名 |
| 凭据泄露 | 环境变量加密、API 脱敏、日志/错误过滤；不记录请求体 |
| CSRF/局域网滥用 | 仅本机 + 自定义动作头 + Origin/Sec-Fetch-Site 校验 |
| 插件不可用拖垮主服务 | 统一超时、响应上限、无默认重试、错误分类、后台循环隔离 |
| 状态漂移 | 启动全量同步 + 周期 Inspect + 以实际为准 |

## 十六、明确不做

- 数据库/ORM、Redis、消息队列、Kubernetes、Compose 编排、多节点调度。
- 插件市场、自动升级、插件间通信、动态 Go Plugin。
- Registry 拉取 API/UI（接口保留，按要求暂缓）。
- 任意 Docker 参数/命令透传、privileged、host 网络、共享目录挂载、Docker Socket 暴露给插件。
- 账号体系、角色权限；管理员边界就是本机。
- 多实例编排（数据结构支持，管理器 v1 单实例）。
- SSE 插件事件（首期轮询）。
